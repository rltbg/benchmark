# Brief v3 — analyse en profondeur d'UN projet (lecture des sources, sans modifier le dépôt)

Contexte : face-à-face Slint / Qt / Avalonia AOT sur des bancs de limites (`v3/docs/BENCH-SPEC-v3.md`, à lire). Tu es l'analyste d'**un** projet. Tu ne compiles pas et ne mesures pas (les implémenteurs et moi le faisons) ; tu lis les sources, la documentation officielle et les outils de profilage du projet pour (1) décrire précisément comment il fonctionne en profondeur, (2) **prédire**, avant toute mesure, où et pourquoi il casse sur chaque famille de scénarios, (3) préparer l'interprétation des profils (`perf record -e cpu-clock -g`).
Machine : disque limité (~9 Go libres, partagés) : clones `--depth 1`, sparse-checkout (`git clone --filter=blob:none --depth 1 --sparse`, puis `git sparse-checkout set <dossiers>`) dans `/opt/src/<projet>/`, jamais dans le dépôt. Clones anonymes autorisés ; les pages web/API de github.com et crates.io web sont bloquées (utilise `raw.githubusercontent.com`, les clones git, docs.rs, doc.qt.io, learn.microsoft.com, docs.avaloniaui.net, docs.slint.dev…).
Écris `v3/docs/deep/<stack>.md` (français) avec, **pour chaque affirmation, le chemin de fichier:ligne (ou symbole) et le commit/tag lu** :
1. **Architecture de rendu** : de « une propriété change » à « un pixel est écrit » ; scène retenue ou mode immédiat ; suivi des zones à redessiner (damage) ; passes ; qui fait quoi sur quel thread ; moteur de rastérisation logicielle (Skia/CPU, renderer maison…) et ses chemins rapides/lents (dégradés, ombres, clips arrondis, groupes d'opacité, images, texte).
2. **Boucle d'événements et cadence** : timers, vsync, coalescence des invalidations, comment une frame est planifiée à 60 Hz sous X11/Xvfb.
3. **Moteur de propriétés / liaisons / réactivité** : coût d'un changement de propriété, propagation, allocation, dépendances ; coût de N liaisons.
4. **Mise en page** : algorithme (flex/grille/empilement), complexité, invalidation, coût du redimensionnement et des grands arbres.
5. **Texte** : mise en forme (HarfBuzz ?), cache de glyphes/lignes, gros documents, édition, bidi/CJK/emoji.
6. **Listes/virtualisation** : composants officiels, hauteurs variables, recyclage, coût d'un reset de modèle, d'une insertion, d'un `dataChanged`.
7. **Images** : décodage (thread ?), cache, mémoire, transformations.
8. **Mémoire et modèle d'exécution** : allocations par frame, GC/arènes/comptage de références, fuites typiques ; pour .NET : NativeAOT, GC concurrent, `GCSettings`, `AppContext` switches.
9. **FFI et fils** : comment on appelle du C, rappels natif→UI, mise en file vers le thread UI, coûts (P/Invoke vs `SuppressGCTransition`, marshalling, `QMetaObject::invokeMethod`, `slint::invoke_from_event_loop`…).
10. **Outils de diagnostic/profilage disponibles** (variables d'environnement, compteurs, journaux de rendu : ex. `SLINT_DEBUG_PERFORMANCE`, `QSG_RENDER_TIMING`/`QSG_VISUALIZE`, métriques Avalonia/EventPipe) et la **suite de benchmarks officielle** du projet (ce que les mainteneurs mesurent : chemins chauds reconnus).
11. **Points de rupture prédits** : un tableau « famille de scénarios (L, T, G, U, F, I, M) → mécanisme probable de rupture → ordre de grandeur attendu de N_max à 60 Hz sur 4 vCPU en rendu logiciel → ce qu'un profil devrait montrer (fonctions/zones dominantes) ». Ce sont des hypothèses falsifiables, datées (écris la date de rédaction) : elles seront comparées aux mesures.
12. **Pièges d'implémentation** que doit éviter quelqu'un qui écrit ces bancs dans ce projet (anti-patterns de performance documentés ou visibles dans le code), pour aider la revue croisée d'équité.
Rapport final ≤ 30 lignes : les 5 constats d'architecture les plus déterminants pour la performance, les 5 prédictions les plus risquées, ce que tu n'as pas pu vérifier.
