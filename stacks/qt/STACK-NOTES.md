## Ce qui est mesure (champ `notes` du JSON)
- `frame_ms` = intervalle entre emissions consecutives de `QQuickWindow::frameSwapped`, **uniquement pour les frames demandees par notre tick** (les frames supplementaires declenchees par ex. par la fin d'un decodage d'image ne sont pas des echantillons). Backend software : emis apres rendu des regions sales par `QSGSoftwareRenderLoop` + flush du `QBackingStore` vers X (xcb, SHM) ; RHI/GL : apres swapBuffers sur le thread de rendu.
- Redessin continu : `frameSwapped` (connexion directe) -> post queued d'un `tick()` sur le thread UI -> script + `window->update()`.
- **Pacing Qt supprime** : Qt cadence les `requestUpdate()` via `QT_QPA_UPDATE_IDLE_TIME` (defaut 5 ms => plafond ~130-200 fps meme pour une scene triviale). L'app met `QT_QPA_UPDATE_IDLE_TIME=0` (qputenv avant QGuiApplication) pour respecter « pas de pacing » ; `--paced` retablit le defaut Qt (smoke list : 132 fps paced vs ~740 fps non paced). Pas de vsync sous Xvfb/software de toute facon.
- Animations (nav) : le loop software de Qt avance les animations sur un timer 16 ms ; j'installe un `QAnimationDriver` « frame-driven » (comme les loops RHI) avance a chaque tick (backend software seulement ; en RHI le driver natif est garde). En nav, si le temps d'animation (resolution ms) n'a pas avance, le tick est reporte de 1 ms au lieu de rendre une frame vide (sinon >40 000 « frames » vides/s).
- Warm-up 2 s (le temps de chargement du texte 1 Mo compte dedans) puis scripts relances a t=0 ; compteurs remis a zero au debut de la mesure. Idle : aucun redessin, QTimer unique (warm-up + duration).

## Implementation par scenario
- **idle** OK : shell (barre titre, ListView 1ere page, barre d'etat), aucune animation.
- **list** OK : QML `ListView` (`reuseItems`, `cacheBuffer 600`, hauteur de delegate = role `rowH`) sur modele C++ `QAbstractListModel` 100 000 lignes calculees dans `data()` (aucun stockage par ligne). Script 4 s @3000 px/s puis 6 flings v0=20000 e^-2t 1,5 s alternes, clamp. `ops.sum_heights`=8799584 (somme calculee en C++ sur les 100k lignes). **Ecart** : `ListView` ne connait qu'un `contentHeight` *estime* (moyenne des delegates vus x 100k : 8,4–9,2 M selon l'instant, vs 8 799 584 exact) ; l'offset scripte `final_offset` est calcule dans l'espace exact (somme des hauteurs) mais `contentY` est borne par l'estimation du ListView (`listview_contentY`, `listview_contentHeight_estimate` fournis). Les sauts de `contentY` lointains font reestimer l'index par Qt ; l'affichage reste coherent localement mais l'index visible a un offset donne n'est pas exactement `prefixe(h)`. `rows_drawn` = nombre d'appels `data(TitleRole)` = creations + rebinds (reuse) de delegates. Sous-titre = une ligne clippee (pas de wrap).
- **stream** OK : producteur `std::thread` xorshift32 seed 0x2545F491 (index = x%100000, prix = x/100.0), lots postes par `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` ; file bornee 100k via compteur « in-flight » atomique (drop + compte cote producteur, jamais bloquant) ; thread UI applique tout le lot a chaque frame (`dataChanged` par update, role Price). `updates_generated/applied/dropped` fournis (1k/s et 10k/s : 0 drop).
- **canvas** OK (2 implementations C++ + 1 QML en fumee) :
  - `painted` (defaut) = `QQuickPaintedItem` (RenderTarget Image) : QPainter -> QImage -> noeud `QSGPainterNode` (une copie en plus). Fonctionne sur tous les backends.
  - `render` = `QSGRenderNode` custom qui dessine directement dans le `QPainter` du renderer software (`QSGRendererInterface::PainterResource`) : pas d'image intermediaire, **software uniquement**. Perf quasi identique (5000 formes : 12.6 vs 14.4 fps, 20000 : 3.6 vs 3.5) car le cout est domine par la rasterisation QPainter (clip AA + degrades), pas par la copie. Bug rencontre : sans `markDirty(DirtyMaterial|DirtyGeometry|DirtyForceUpdate)` sur le noeud, le renderer software ne repeint pas (fps faux ~184, rien ne bouge) — corrige.
  - Choix : les custom `QSGGeometryNode`+materiau ne sont pas executables en backend software (pas de shaders) ; donc QPainter (immediat) est l'idiome performant ici. `painted` est le defaut car portable (RHI inclus).
  - Dessin : N formes (1/3 rect, 1/3 cercles, 1/3 rect arrondis, tailles 16..72 px issues de fnv), rebond dans la zone clippee 1000x600 (rect arrondi r=24, `setClipPath` anti-alias), degrade lineaire 2 couleurs par forme (`QLinearGradient` ObjectBoundingMode, brosse pre-construite), 1 forme sur 10 avec ombre (flou 8 px, offset 2,2) = **sprite pre-flou (3 box blurs) mis en cache par (type,taille)** car QPainter n'a pas de primitive de flou (les formes elles-memes sont vectorielles a chaque frame) ; graphe polyligne 10 000 points (1 point/frame) dans 1000x100 sous la zone. Mouvement dt-based (vitesse 40..200 px/s).
  - `qml` (`Canvas` JS Context2D, renderTarget Image, Cooperative) : fumee seulement, memes formes/degrades/ombres natives du Context2D : **3.5 fps a 1000 formes** vs 65 fps pour `painted` a 1000 formes et 12.6 fps a 5000 (soit ~20x plus lent par forme).
- **text** OK : `TextEdit` readOnly + `selectByMouse` dans un `Flickable`, 1 Mo UTF-8 (mix CJK/arabe/emoji), scroll aller-retour 3000 px/s, `selectAll()` a t=5 s (verifie visuellement). `layout_ms` ~1,0 s (pose du texte + layout synchrone complet), `time_to_first_display_ms` ~1,0–1,2 s. L'IME n'est pas automatisee (protocole manuel hors perimetre).
- **images** OK : `GridView` 10 colonnes 128 px, 600 `Image{asynchronous, sourceSize 128x128}` via `QQuickImageProvider` (decodage PNG + reduction lissee dans le thread de chargement d'images de Qt, chronometre dans le provider -> `decode_total_ms` = vrai temps de decodage cumule, ~2,5–3 ms/image). Zoom = `scale` 1->3->1 sur 6 s (transformOrigin centre) + scroll 3000 px/s aller-retour. `images_decoded` > 600 car les pixmaps sortis du cache sont redecodes au retour du scroll (`*_incl_warmup` aussi fournis).
- **nav** OK (sans Controls, voir plus haut) : 3 ecrans (14 lignes chacun), cycle [push, push, modal ouvre/ferme (fondu 200 ms), pop, pop], glissements 300 ms, thread C++ en boucle de calcul (~1 cœur). `transitions_done` + `modals_done` (20 transitions en ~8 s de mesure : 19–20).
- **core** OK : 2 threads std::thread (boucle serree validate+parse+hash sur la trame hello de 8 octets, compteur par lots de 2000 ; `core_heavy(100)` chaque seconde) ; UI anime 1000 formes (canvas sans graphe). `calls_per_s` ~65–110 M/s (varie avec la charge de la machine), `max_frame_stall_ms` = max frame_ms.
- **stress** OK : list(880 px) + stream 5000/s + canvas 5000 formes (panneau 400x720) + core. ~9–13 fps (dominé par le canvas software). Pas de tas manage : `managed_heap_kb` **non fourni** (pas de runtime manage ; echantillons RSS = harnais). Duree par defaut non codee en dur (utiliser `--duration 600`).
