## 1. Architecture de rendu : de « une propriété change » à « un pixel est écrit »

### 1.1 Chaîne complète (backend software, boucle `basic` par défaut)

1. **Setter de propriété d'Item** (`x`, `opacity`, `text`…) → `QQuickItemPrivate::dirty(attr)` → l'item est mis en liste chaînée `dirtyItemList` de la fenêtre et `QQuickWindow::maybeUpdate()` est appelé (`ITEMS:qquickwindow.cpp:884-896` `dirtyItem`, `ITEMS:qquickwindow.cpp:2491-2497` `maybeUpdate` → `windowManager->maybeUpdate`). `QQuickItem::update()` ne fait que `dirty(Content)` (`ITEMS:qquickitem.cpp:4666-4676`) ; `polish()` met l'item dans `itemsToPolish` et appelle `maybeUpdate` seulement si la liste était vide (`ITEMS:qquickitem.cpp:4686-4698`).
2. **Planification** : `QSGSoftwareRenderLoop::maybeUpdate` pose `updatePending=true` et appelle `window->requestUpdate()` (`SW:qsgsoftwarerenderloop.cpp:232-239`). `QWindow::requestUpdate` est idempotent tant qu'une requête est en attente (`GKERN:qwindow.cpp:2885-2895`), puis `QPlatformWindow::requestUpdate` démarre un `QBasicTimer` **PreciseTimer de 5 ms** (ou `QT_QPA_UPDATE_IDLE_TIME`, 0 autorisé) (`GKERN:qplatformwindow.cpp:781-799`). Le plugin xcb ne redéfinit pas `requestUpdate` (grep sans résultat dans `XCB:*.cpp`) : **aucun vsync, aucun frame callback** [lu].
3. **Livraison** : `QEvent::UpdateRequest` → `QQuickWindow::event` → `windowManager->handleUpdateRequest` (`ITEMS:qquickwindow.cpp:1682-1684`) → `QSGSoftwareRenderLoop::renderWindow` (`SW:qsgsoftwarerenderloop.cpp:77-194`) qui exécute, **sur le thread GUI** : `flushFrameSynchronousEvents` (événements d'entrée compressés, l.102) → `polishItems` (l.117 ; `ITEMS:qquickwindow.cpp:331-352`, `takeLast` jusqu'à vider la liste) → signal `afterAnimating` (l.127) → `syncSceneGraph` (l.131 ; `ITEMS:qquickwindow.cpp:525-570` → `updateDirtyNodes` l.2151-2168 → `updateDirtyNode` par item sale, qui appelle `updatePaintNode` des items `ItemHasContents` et recalcule la **matrice en `QMatrix4x4` (float32)**, `ITEMS:qquickwindow.cpp:2225-2246`) → `renderSceneGraph` (l.146) → `QBackingStore::flush(flushRegion)` + `fireFrameSwapped` (l.160-167).
4. **Rendu** : `QSGSoftwareRenderer::render` (`SW:qsgsoftwarerenderer.cpp:67-155`) = `buildRenderList` (l.116) → `optimizeRenderList` (l.128) → `QBackingStore::beginPaint(updateRegion)` (l.134) → `QPainter painter(paintDevice)` avec `Antialiasing` **activé globalement** (l.139-140) → `renderNodes` (l.146) → `endPaint`.
5. **Présentation** : `QXcbBackingStore::flush` (`XCB:qxcbbackingstore.cpp:832-865`) → `m_image->put` → `xcb_shm_put_image` **une requête par rectangle de la `QRegion` sale** (`XCB:qxcbbackingstore.cpp:569-588`) puis `xcb_flush` (ou `updateSyncRequestCounter` si le WM l'exige, l.860-863). Si la mémoire partagée MIT-SHM est indisponible : repli `xcb_image_put` par bandes (`XCB:qxcbbackingstore.cpp:590-648`).

`frameSwapped` est émis **juste après l'envoi** des requêtes X (pas d'attente du serveur) : `frame_ms` mesuré par `frameSwapped` ne voit pas le temps de Xvfb [lu+inf].

### 1.2 Scène retenue, boucles disponibles

- Mode **retenu** (scene graph) : arbre de `QSGNode` (transform/clip/opacity/geometry/glyph…) conservé entre frames ; seuls les items sales sont resynchronisés (`dirtyItemList`, `ITEMS:qquickwindow.cpp:2151-2168`).
- Le backend est choisi par `QT_QUICK_BACKEND` (ou `QMLSCENE_DEVICE`) (`QD:src/quick/scenegraph/qsgcontextplugin.cpp:97`) ; par défaut seulement si Qt est compilé sans OpenGL/Vulkan/Metal (même fichier l.99-105).
- Boucle : `QSGSoftwareRenderLoop` (GUI thread, tout séquentiel) ; la variante `QSGSoftwareThreadedRenderLoop` n'est choisie que si `QSG_RENDER_LOOP=threaded` (`SW:qsgsoftwareadaptation.cpp:39-57`). Dans la variante threadée, le thread de rendu rend puis **dort pour finir l'intervalle `1000/refreshRate` (16 ms)** (`SW:qsgsoftwarethreadedrenderloop.cpp:413-490`, `qsgrl_animation_interval` l.120-124) et le thread GUI est bloqué pendant `sync` (`polishAndSync` l.899+). Gain potentiel : recouvrement GUI(événements/liaisons) // rendu ; coût : plafond de cadence 62,5 Hz propre à cette boucle [lu+inf].

### 1.3 Suivi des zones sales (damage) — le cœur de la performance software

Structure : `QSGSoftwareRenderableNode` par nœud « dessinable » (rect, image, glyphes, painter, render node…) stocké dans `QHash<QSGNode*,QSGSoftwareRenderableNode*> m_nodes` (`SW:qsgabstractsoftwarerenderer.cpp:51-54`) ; liste de rendu `m_renderableNodes` reconstruite **à chaque frame** par une visite de **tout l'arbre** (`buildRenderList`, `SW:qsgabstractsoftwarerenderer.cpp:113-121`, visiteur `SW:qsgsoftwarerenderlistbuilder.cpp`, un `QHash::value` par nœud dessinable).

Propagation d'un changement :
- `QSGAbstractSoftwareRenderer::nodeChanged` (`SW:qsgabstractsoftwarerenderer.cpp:61-88`) : géométrie/matériau → `markGeometryDirty/markMaterialDirty` du nœud ; **matrice ou opacité → `m_nodeUpdater->updateNodes(node)` = re-visite de tout le sous-arbre** (l.304-318, `SW:qsgsoftwarerenderablenodeupdater.cpp:170-242`).
- `updateRenderableNode` appelle **inconditionnellement** `renderableNode->update()` après `setTransform/setOpacity/setClipRegion` (`SW:qsgsoftwarerenderablenodeupdater_p.h:86-104`) ; `update()` fixe `m_isDirty = true`, recalcule `boundingRectMin/Max` et alloue `m_dirtyRegion = QRegion(boundingRectMax)` (`SW:qsgsoftwarerenderablenode.cpp:98-197`). Conséquence **[lu+inf]** : déplacer un conteneur (par exemple le `contentItem` d'un `Flickable`/`ListView`) **marque sales et repeint tous les nœuds descendants** ; il n'existe aucun blit de défilement (`QBackingStore::scroll` n'est pas appelé dans `SW:`).
- `optimizeRenderList` (`SW:qsgabstractsoftwarerenderer.cpp:123-216`) : deux passes sur toute la liste. Passe avant→arrière inversée (du plus haut au plus bas) : `addDirtyRegion(m_dirtyRegion)`, `subtractDirtyRegion(m_obscuredRegion)`, accumulation `m_obscuredRegion += boundingRectMin` pour chaque nœud **opaque** (même non sale, l.144-146), `m_dirtyRegion += boundingRectMax; -= boundingRectMin` pour un nœud opaque sale (l.159-166) ou `+= dirtyRegion` (nœud translucide, l.169). Seconde passe : tout nœud non opaque (ou à rect flottant) sous une zone sale est re-marqué sale (l.194-207). Les opérations `QRegion` (`+=`, `-=`, `intersected`, `intersects`) sont des opérations sur listes de rectangles *y-x banded* : chemin rapide « contains/append/prepend » sinon `UnionRegion` = fusion linéaire en nombre de rectangles (`PAINT:qregion.cpp:3957-4046`, `miRegionOp` l.2102). **[inf]** coût de `optimizeRenderList` ≈ O(nœuds × complexité de région), donc **quadratique** quand beaucoup de petits nœuds dispersés sont sales (région de 2·N rectangles).
- Chaque nœud sale est peint avec `painter->save(); setOpacity; setClipRegion(m_dirtyRegion, ReplaceClip); setTransform; …; restore()` (`SW:qsgsoftwarerenderablenode.cpp:254-313`). Si `m_dirtyRegion` a plus d'un rectangle, `QClipData::setClipRegion` passe en clip « région » (`PAINT:qpaintengine_raster.cpp:3994-4018`) et `QClipData::initialize` alloue **`(ymax−ymin) × numRects` spans** de 16 octets au premier tracé qui utilise des spans (`PAINT:qpaintengine_raster.cpp:3804-3822`) : un grand nœud de fond sous N formes sales (fond clair de la fenêtre, `m_background->renderNode(painter, true)`, `SW:qsgabstractsoftwarerenderer.cpp:99-102`) coûte **O(hauteur × N)** par frame [inf].
- `QSG_SOFTWARE_RENDERER_FORCE_PARTIAL_UPDATES=0` désactive les mises à jour partielles (`markDirty()` plein cadre à chaque frame, `SW:qsgsoftwarerenderer.cpp:27-33,99-107`), documenté (`QD:src/quick/doc/src/concepts/visualcanvas/adaptations.qdoc:105-113`) ; `=1` les force malgré un DPR fractionnaire (`adaptations.qdoc:133-141`). Désactivées d'office si le DPR n'est pas entier (`SW:qsgsoftwarerenderer.cpp:100-103`).
- Aucune réutilisation de pixels entre frames hors du backing store : `QBackingStore` conserve l'image, seule la région sale est repeinte et poussée (`beginPaint(updateRegion)`).

### 1.5 Qui fait quoi sur quel thread

- Boucle `basic` (défaut) : **tout sur le thread GUI** (événements, animations, liaisons JS, polish, sync, raster, envoi X). Seuls des fils annexes : thread de lecture des événements XCB `QXcbEventQueue::run` (`XCB:qxcbeventqueue.cpp:178-212` → `wakeUpDispatcher`, l.215-222), thread du lecteur d'images `QQuickPixmapReader` (priorité la plus basse, un par moteur, `UTIL:qquickpixmapcache.cpp:225,597-612`), threads utilisateur.
- Xvfb est **un autre processus** qui consomme du CPU pour recopier les `shm_put_image` : il partage les 4 vCPU avec l'app et le harnais [inf].
- Raster **mono-thread** : aucune parallélisation du remplissage dans `QRasterPaintEngine` [lu : un seul `QPainter`/`QRasterPaintEngine` par frame] ; la parallélisation possible est `QSG_RENDER_LOOP=threaded` (GUI // rendu) ou `Canvas.Threaded` (rejeu des commandes dans un fil privé, `qquickcanvasitem.cpp:484-486`).

### 1.6 Écarts de fidélité visuelle propres au backend (utiles à la revue d'équité)

1. Pas d'ombre/flou/MultiEffect : ces variantes sont `unsupported` ou doivent être simulées (sprite pré-flouté, ce que `V2` stacks/qt a déjà choisi) — **à signaler**, ce n'est pas l'API officielle de Qt Quick pour l'ombre.
2. Opacité de groupe fausse sans `layer.enabled` (recouvrements visibles).
3. Clip arrondi = rectangle.
4. **Positions en float32** : la matrice de chaque item est un `QMatrix4x4` (`float m[4][4]`, `QB:src/gui/math3d/qmatrix4x4.h:185`) construite par `translate(x,y)` avec des `qreal` tronqués en `float` (`ITEMS:qquickwindow.cpp:2231`) puis convertie par `toTransform()` (`QB:src/gui/math3d/qmatrix4x4.cpp:1652-1657`). Pour une `ListView` dont `contentHeight` ≈ 8,8·10⁶ px (100 k lignes de ~88 px) l'ulp float vaut 1 px ; pour 1 M lignes (≈8,8·10⁷) 8 px ; pour 10 M lignes (≈8,8·10⁸) **64 px** [calcul : ulp = 2^(⌊log2 v⌋−23)]. Les lignes sont donc alignées sur une grille de 8 à 64 px relativement au `contentItem` (qui subit la même quantification) : chevauchements/trous et défilement par pas **[inf, à vérifier par capture]**. Aucun contournement public.

### 1.7 Backend RHI (OpenGL/Vulkan sur llvmpipe/lavapipe) — survol [nl pour le détail]

`QSGBatchRenderer` (`QD:src/quick/scenegraph/coreapi/qsgbatchrenderer.cpp`, 4347 lignes, non lu en détail) regroupe opaques/alpha en lots, variables `QSG_RENDERER_DEBUG` (l.34), `QSG_VISUALIZE` (`ITEMS:qquickwindow.cpp:800`), `QSG_RHI_BACKEND`, `QSG_INFO`, `QSG_RHI_PREFER_SOFTWARE_RENDERER`. Sous llvmpipe le coût est celui de l'émulation shader CPU, pas celui du code Qt. `V2` : `qt-opengl` list 60 fps mais CPU 57 % contre 9 % en software (`stacks/qt/STACK-NOTES.md`).

## 2. Boucle d'événements et cadence

**Dispatcher** : `QEventDispatcherGlib` si Qt est construit avec glib (le déploiement `V2` lie glib, `stacks/qt/STACK-NOTES.md` § Déploiement), sinon `QEventDispatcherUNIX` ; `wakeUp()` glib = `g_main_context_wakeup` à **chaque** `postEvent` (`KERN:qeventdispatcher_glib.cpp:567-572`) [lu ; coût d'appel système par réveil : glib non lu].

**Minuteurs** : `QTimerInfoList` trie les timers par échéance ; `PreciseTimer` = précision milliseconde ; réarmement `timeout += interval` puis, **si en retard, `timeout = now + interval`** (pas de rattrapage, `KERN:qtimerinfo_unix.cpp:212-228`) ; `CoarseTimer` ≤ 20 ms est converti en `PreciseTimer` (l.282-291). Un minuteur de 4 ms (spec `ui_stall_ms_max`) est donc exact à ±1 ms tant que le thread GUI revient à la boucle.

**Animations** : `QUnifiedTimer` + driver par défaut `QDefaultAnimationDriver` : `DEFAULT_TIMER_INTERVAL = 16` ms (`QB:src/corelib/animation/qabstractanimation.cpp:128,886-906`, `m_timer.start(interval, Qt::PreciseTimer)`). La boucle `basic` **n'installe pas de driver** (« Animations are advanced using the standard timer », `QD:src/quick/scenegraph/qsgrenderloop.cpp:57-59` ; `SW:qsgsoftwarerenderloop.cpp` ne crée aucun `QAnimationDriver`) : cadence nominale **62,5 Hz** (16 ms entiers), indépendante du rendu ; si une frame dure >16 ms le tick suivant est décalé (pas de rattrapage) et les animations sont **basées sur le temps écoulé** (interpolations correctes, frames sautées, pas de ralenti).

**Séquence d'une frame animée** : tick animation (t) → propriétés écrites → `maybeUpdate` → `requestUpdate` (timer 5 ms, ou 0 si `QT_QPA_UPDATE_IDLE_TIME=0`) → `UpdateRequest` → polish/sync/render/flush. Cadence effective : le **tick 16 ms** ; le délai 5 ms s'ajoute à la latence mais pas au débit. Sans animation, toute modification d'item déclenche une frame **au plus tous les 5 ms** (≤ 200 Hz), ou en continu avec `QT_QPA_UPDATE_IDLE_TIME=0` ; `QD:src/quick/doc/src/concepts/visualcanvas/scenegraph.qdoc:432-451` recommande ce réglage pour le benchmark bas niveau. `V2` : 700–1 100 fps en `uncapped` avec ce réglage ; 149 fps avec le défaut 5 ms.

**Coalescence** : `requestUpdate` idempotent (une `UpdateRequest` par frame) ; `QSGRenderer::nodeChanged` n'émet `sceneGraphChanged` qu'une fois par frame (`QD:src/quick/scenegraph/coreapi/qsgrenderer.cpp:208-212`) ; événements de pointeur compressés au début de la frame (`flushFrameSynchronousEvents`, `SW:qsgsoftwarerenderloop.cpp:102`) ; `QCoreApplication::postEvent` compresse seulement `Timer` et `Quit` (`KERN:qcoreapplication.cpp:1744-1780`) — **pas** les `QMetaCallEvent`.

**Sous Xvfb sans gestionnaire de fenêtres** : pas de `_NET_WM_SYNC_REQUEST` (`needsSync()` faux) donc `xcb_flush` seul (`XCB:qxcbbackingstore.cpp:860-863`) [inf].

**Boucle threadée logicielle** (`QSG_RENDER_LOOP=threaded`) : animations avancées dans le thread de rendu pour les `Animator` (`rtAnim->advance()` dans `syncAndRender`, `SW:qsgsoftwarethreadedrenderloop.cpp:452-454`) ; plafond 16 ms par `msleep` (l.476-481).

## 3. Moteur de propriétés, liaisons, réactivité

- **Changement d'une propriété `Q_PROPERTY` notifiée** : `QMetaObject::activate` → `QQmlData::signalEmitted` → `QQmlNotifier::emitNotify` (`QML:qqmlnotifier.cpp:44-80`) : parcours de la liste chaînée d'« endpoints » ; copie préalable des `N` endpoints dans un `QVarLengthArray` (pile dynamique), puis rappels `QQmlJavaScriptExpressionGuard_callback` → `QQmlJavaScriptExpression::expressionChanged()` (`QML:qqmljavascriptexpression.cpp:564-570`). **Coût O(N endpoints) par émission, dont une allocation si N dépasse la capacité inline** [lu].
- **Réévaluation d'une liaison** : `QQmlBinding::update` (`QML:qqmlbinding.cpp:134-176`) → `doUpdate` (l.681-720) → `QQmlJavaScriptExpression::evaluate` (`QML:qqmljavascriptexpression.cpp:214-252`) : `QQmlJavaScriptExpressionCapture` (capture des dépendances), wrapper `QObjectWrapper` du `this` (allocation GC possible), appel de `QV4::Function::call` ; les **gardes de dépendance sont réutilisées** si l'ensemble des dépendances est stable (`QML:qqmljavascriptexpression.cpp:422-440`) → pas d'allocation par réévaluation stable ; écriture typée via `write()` (`QML:qqmlbinding.cpp:204-300`), repli `slowWrite` si conversion nécessaire (l.430-560).
- **Exécution du code** : liaisons compilées par `qmlcachegen`/`qmlsc` ; fonctions typées éligibles **AOT en C++** (`QV4::Function::aotCompiledFunction`, `QML:qqmlbinding.cpp:691`, `QD:src/qml/jsruntime/qv4function.cpp:62,84-138`) sinon **interpréteur + JIT de base** : seuil `QV4_JIT_CALL_THRESHOLD`, **3 appels** par défaut (`QD:src/qml/jsruntime/qv4engine.cpp:341-345`), `QV4_FORCE_INTERPRETER` pour le désactiver.
- **Propriétés « bindable » (`QProperty`)** : une liaison dont la cible est bindable devient un `QQmlPropertyBinding` (`QPropertyBindingPrivate`, `QML:qqmlpropertybinding.cpp:24-120`) ; la capture d'une source bindable passe par `captureBindableProperty` (`QML:qqmljavascriptexpression.cpp:385-398`) avec un `QPropertyChangeTrigger` puisé dans un pool (l.547-556). `QQmlPropertyBindingJS::expressionChanged` détecte les boucles (l.135-163). Coûts : `QQmlPropertyBinding::evaluateRecursive/notifyNonRecursive` en plus d'une évaluation JS ; **pas d'économie d'évaluation** par rapport au chemin signal (la dépendance reste JS) [inf].
- **Coût d'un changement** vers une liaison de `Text.text` : (1) `emitNotify` ; (2) évaluation JS/AOT ; (3) `QQuickText::setText` : **`Qt::mightBeRichText` si `textFormat` = `AutoText` (défaut)** (`ITEMS:qquicktext.cpp:55,1846`), mise en page synchrone `updateLayout` (`ITEMS:qquicktext.cpp:214-…`), invalidation de taille, `polish` ; (4) à la synchro : reconstruction du nœud glyphes (`ITEMS:qquicktext.cpp:2600-2680`, `node->recycle`) ; (5) rendu §1.3. L'ordre de grandeur est dominé par (3)-(5), pas par (1)-(2) [inf].
- **Coût de N liaisons** : linéaire en N pour N liaisons sur *une* source (`emitNotify` O(N)) ; si N sources distinctes changent, N appels `emitNotify` courts. Tas JS : chaque `QObject` touché par JS reçoit un wrapper géré par le GC.
- **Animations** : `QQuickBulkValueAnimator::updateCurrentTime` → `QQuickAnimationPropertyUpdater::setValue` (`UTIL:qquickanimation.cpp:2062-2072,2704-2750`) : par action et par tick = interpolation en `QVariant` + `QQmlPropertyPrivate::write(..., BypassInterceptor|DontRemoveBinding)` (écriture via `QVariant`, pas de liaison créée). `Animator` (`XAnimator`, `OpacityAnimator`…) pilotés par `QQuickAnimatorController`, `animationController->advance()` dans `renderSceneGraph` (`ITEMS:qquickwindow.cpp:667`) : agissent sur les nœuds sans passer par les propriétés (les valeurs d'item ne sont pas mises à jour) [lu partiel].

**Allocation** : QRegion par `update()` de nœud, `QPainterState` par `save()`, `QHash` d'états (`m_stateMap`) : pas de pool [inf].

## 4. Mise en page

- **Pas de moteur de mise en page global** : chaque item porte `x/y/width/height` ; l'« empilement » et la grille sont des items spécialisés. `Row/Column/Grid/Flow` (`ITEMS:qquickpositioners.cpp`) recalculent dans `updatePolish` : `prePositioning` parcourt tous les enfants (`ITEMS:qquickpositioners.cpp:158,283`), déclenché par tout changement de taille/visibilité d'un enfant → O(enfants) par positionneur et par frame sale. `Anchors` : `QQuickAnchorsPrivate::update/updateVerticalAnchors/updateHorizontalAnchors` sur `itemGeometryChanged` (`ITEMS:qquickanchors.cpp:435-460,572,659`) : propagation en cascade O(arbre dépendant) à chaque changement de taille de la cible ; les `anchors` sont plus rapides que des liaisons `x: parent.width/2` (doc : `QD:src/quick/doc/src/concepts/performance/performance.qdoc:593-640`). `QtQuick.Layouts` : **[nl]**.
- **Redimensionnement de la fenêtre** : `QQuickWindow::resizeEvent` → `contentItem` redimensionné → chaque item lié (`anchors.fill`, `width: parent.width`) est réévalué ; côté rendu : `setBackgroundRect` → **`markDirty()` plein cadre** (`SW:qsgabstractsoftwarerenderer.cpp:226-235`), redimensionnement du backing store XCB (réallocation du segment SHM si la taille change de plus d'un facteur 2, `XCB:qxcbbackingstore.cpp:196-250,896-…`), donc repeinture complète + `buildRenderList`/`optimizeRenderList` sur **tout** l'arbre, y compris hors écran (les nœuds hors fenêtre sont tout de même visités, `SW:qsgabstractsoftwarerenderer.cpp:148-157`).
- **Complexité** : coût de la frame suivant un redimensionnement ≈ `O(nœuds dessinables)` pour les listes + `O(nœuds visibles × coût de tracé)` ; pas de mise en cache de mise en page entre tailles [inf].
- **Grands arbres** : `QQuickItem` + `QQuickItemPrivate` + `QQmlData` + contextes ; création : `QQmlObjectCreator` (`QML:qqmlobjectcreator.cpp`, [nl en détail]) ; invisibles (`visible:false`) ne génèrent pas de nœuds (`ITEMS:qquickwindow.cpp:2186-2210`, `fetchNextNode` ignore `!explicitVisible`) mais gardent leurs liaisons actives (doc `performance.qdoc:853-863`).

## 6. Listes et virtualisation

**Composants** : `ListView`/`GridView` (`QQuickItemView`, `ITEMS:qquickitemview.cpp`, `ITEMS:qquicklistview.cpp`), `TableView` ; modèle via `QQmlDelegateModel` (`QMLM:qqmldelegatemodel.cpp`) avec adaptateur `QQmlAdaptorModel` ; `Repeater` non virtualisé.

**Algorithme** (`QQuickItemViewPrivate::refill`, `ITEMS:qquickitemview.cpp:1910-1975`) : fenêtre `[pos − displayMarginBeginning, pos + displayMarginEnd + taille]` ; `addVisibleItems` crée les délégués manquants (`createItem` → `model->object(index, incubationMode)`, `ITEMS:qquickitemview.cpp:2525-2575`), `removeNonVisibleItems` libère les autres, puis `layoutVisibleItems`. **`cacheBuffer` par défaut = 320 px** (`ITEMS:qquickitemview.cpp:17-20`) : préremplissage **asynchrone** (`bufferPause` = `QPauseAnimationJob` de 16 ms, l.1684-1686,1955-1959). **`reuseItems` est faux par défaut** (`ITEMS:qquickitemview_p_p.h:286`) : sans lui chaque délégué sorti est détruit et chaque entrant recréé ; avec lui le délégué passe par `QQmlReusableDelegateModelItemsPool` (`QMLM:qqmldelegatemodel.cpp:3961-4060`, taille illimitée `MaxSize = INT_MAX`, `takeItem` en parcours linéaire du pool) et `reuseItem` (l.1108) remet à jour index/rôles/liaisons ; `drainReusableItemsPool` (l.1147).

**Hauteurs variables, estimation de `contentHeight`** (`ITEMS:qquicklistview.cpp`) : `averageSize` initial **100,0** (l.164) puis moyenne des délégués visibles (`updateAverage`, l.1486-1494 ; `layoutVisibleItems` l.883-919) ; `lastPosition()` extrapole `invisibleCount × (averageSize + spacing)` (l.506-531) ; saut de plus d'une page : `count = (fillFrom − itemEnd)/(averageSize+spacing)` (l.743-757) : **la ligne atteinte après un saut est estimée, pas exacte**. Conséquences : `contentHeight`, la barre de défilement et `contentY ↔ index` sont des approximations (la doc officielle le dit : `V2` revue §4) ; une somme exacte des hauteurs (`ops.sum_heights`) doit être calculée côté modèle, pas lue sur la vue.

**Reset de modèle** : `QQmlDelegateModel::_q_modelAboutToBeReset` + `handleModelReset` (`QMLM:qqmldelegatemodel.cpp:1983-2054`) : O(taille du cache) pour invalider les délégués vivants + 1 `listItemsRemoved(0,old)`/`listItemsInserted(0,new)` du compositeur (O(plages)) ; côté vue `modelUpdated(reset=true)` fait **`cancelFlick()` puis `regenerate()`** (`ITEMS:qquickitemview.cpp:1370-1388,1987-2003`) = destruction de tous les délégués, **retour au début** (`setPosition(contentStartOffset())`) et recréation. Donc : (1) le coût d'un reset est indépendant du nombre de lignes tant que le modèle C++ renvoie `rowCount()` en O(1) ; (2) le défilement en cours est perdu (l'élan d'un fling, et le `contentY`) ; (3) un modèle QML `ListModel`/tableau JS de 1 M éléments est construit élément par élément (`performance.qdoc:688-720` : `ListModel` « pas adapté aux grandes quantités »).

**Insertion/suppression** : `_q_itemsInserted` met à jour `m_cache` par `QList::mid` (copie O(cache), `QMLM:qqmldelegatemodel.cpp:1629`) ; la vue applique des `QQmlChangeSet` (`ITEMS:qquickitemview.cpp:1389-1401`).

**`dataChanged`** : `QQmlDelegateModel::_q_dataChanged` → `_q_itemsChanged` (l.1531, 2138-2143) → `QQmlAdaptorModel::notify` **parcourt tout le cache de délégués vivants** (`QMLM:qqmldmabstractitemmodeldata_p.h:106-150`) → `QMetaObject::activate` sur chaque délégué dont l'index est dans la plage, pour chaque rôle ; coût **O(|cache|) par appel**, quel que soit le nombre de lignes modifiées, même si elles sont hors écran [lu]. Puis `emitChanges` → `modelUpdated` → `currentChanges.applyChanges(changeSet)` : `QQmlChangeSet::apply/change` fusionnent dans une **liste triée parcourue depuis le début avec insertion au milieu** (`QMLM:qqmlchangeset.cpp:123-132,471-520`) → **coût O(#changements en attente) par `dataChanged`** ; ces changements s'accumulent jusqu'au prochain polish (`QQuickItemView::modelUpdated` appelle `polish()`, l.1401). **[inf]** : N modifications ponctuelles dispersées par frame coûtent O(N²) par frame (voir §11 L3).

**Défilement** : `Flickable` : vitesse max **2 500 px/s** et décélération **1 500 px/s²** par défaut (`QB:src/gui/kernel/qplatformintegration.cpp:446`, `QB:src/gui/kernel/qplatformtheme.cpp:705-708` ; lus dans `ITEMS:qquickflickable.cpp:252-254`), écrêtage des échantillons de vitesse (l.299-304,396-400) : il faut régler `maximumFlickVelocity`/`flickDeceleration` ou piloter `contentY` pour atteindre 30 000–150 000 px/s. `contentItem->setY(effectiveY)` (`ITEMS:qquickflickable.cpp:2077`) → matrice → repeinture de tout le sous-arbre (§1.3).

## 8. Mémoire et modèle d'exécution

- **C++ natif** : pas de GC global ; objets `QObject` possédés par arbre parent/enfant ; `QSharedData` pour `QString/QImage/QRegion` (copie sur écriture). Chaque nœud dessinable a un objet `QSGSoftwareRenderableNode` (région, transform, clip) + entrées de table de hachage (`m_nodes`, `m_stateMap`) : coût mémoire/nœud de l'ordre de plusieurs centaines d'octets en plus du `QQuickItem` [est].
- **Moteur JS (QV4)** : tas géré, marquage/balayage **incrémental** ; limite de temps par tranche `(1000/60)/3 = 5 ms` par défaut, réglable par `QV4_GC_TIMELIMIT` (`QD:src/qml/memory/qv4mm.cpp:1507-1520`) ; catégories `qt.qml.gc.statistics|allocatorStats|stateTransitions|forcedRuns|stepExecution` (l.61-65). Objets C++ touchés par JS : `QObjectWrapper` (`HandleQObjectWrappers` dans la machine d'états de GC, l.1041).
- **Par frame** : `QRegion` par mise à jour de nœud, `QPainterState` par `save()` (un par nœud peint), `QStack/QHash` du `NodeUpdater`, `QVarLengthArray` des notifieurs (§3) ; recyclage de nœuds de texte via `RecycleBin` (`ITEMS:qquicktext.cpp:2634,2683`) ; pas de pool généralisé [inf].
- **Fuites/dérives typiques** (à surveiller en M1) : `QQmlReusableDelegateModelItemsPool` non borné, `QUndoStack` du `QTextDocument` (par défaut activé), `QQuickPixmapStore` (30 s), `QImageTextureGlyphCache` (grandit avec polices×tailles×positions sous-pixel), `QGradientCache` (60 entrées), tas JS ; **aucune fuite structurelle identifiée dans le code lu** [nl pour le reste].
- Compilation QML : `qt_add_qml_module` + `qmlcachegen` (déjà utilisé, `V2` revue §8) évite l'analyse au runtime ; `QML_DISABLE_DISK_CACHE` n'est pas concerné.

## 9. FFI et fils

- **Appel du cœur C** : fonctions C `extern "C"` liées **statiquement** (`V2` : `libbenchcore.a`), appel direct depuis C++ = appel de fonction ordinaire, sans marshalling ni transition. Depuis QML, il faut une surface `Q_INVOKABLE`/slot : `QMetaObject::metacall` + conversion d'arguments JS→C++ (`QV4::QObjectMethod`), ordre de grandeur **0,3–1 µs par appel [est]** (source : `QD:src/qml/jsruntime/qv4qobjectwrapper.cpp` **[nl]**) ; avec `qmlsc`/types connus l'appel peut être direct. F1 doit appeler le cœur **depuis des fils C++** (`QThread`/`std::thread`) sinon on mesure QML.
- **Rappel natif → UI** : `QMetaObject::invokeMethod(obj, …, Qt::QueuedConnection)` (`KERN:qmetaobject.cpp:1678,1718`) ou signal en connexion queued (`KERN:qobject.cpp:4249-4296` `queued_activate` : alloue un `QQueuedMetaCallEvent` + copie d'arguments typés). Chemin `postEvent` : verrou de la liste d'événements du fil destinataire, **allocation de l'événement**, `postEvent` → `wakeUp()` (`KERN:qcoreapplication.cpp:1685-1731`) ; consommation : `sendPostedEvents` → `QMetaCallEvent::placeMetaCall` (`KERN:qobject.cpp:553`) puis destruction. Coût **producteur ≈ 0,3–1 µs/événement** (malloc + verrou + réveil) et **consommateur ≈ 0,2–0,5 µs + travail du slot [est]** ; la file `QPostEventList` n'a **aucune borne** (croissance mémoire sans limite si le fil GUI ne suit pas).
- **Blocage UI** : `core_heavy(N)` sur le fil GUI gèle tout (événements, rendu, animations). Sur un fil de fond (`QThread`/`QtConcurrent::run`) l'UI n'est impactée que par la compétition CPU (4 vCPU partagés avec Xvfb et le harnais).
- `QQuickWindow::beforeRendering/afterSynchronizing` + `scheduleRenderJob` pour du travail côté rendu (`ITEMS:qquickwindow.cpp:4129` `runAndClearJobs`) ; `WorkerScript` crée un moteur JS par fil (`performance.qdoc:694-706`).

## 12. Pièges d'implémentation (revue croisée d'équité)

**Pièges de performance spécifiques à Qt (documentés ou lisibles dans le code)**

1. `ListView` : **laisser `reuseItems` à faux** ⇒ création/destruction de délégués à chaque frame (`ITEMS:qquickitemview_p_p.h:286`) ; mettre `cacheBuffer` ≥ 0 selon la doc (`performance.qdoc:740-756`) ; **ne pas** utiliser `clip: true` dans un délégué (`performance.qdoc:737,841-851`).
2. **Lire la somme des hauteurs sur la vue** : `contentHeight`/`contentY` sont estimés (§6) ; la doc (`ListView#variable-delegate-size…`) le dit ; calculer `sum_heights` dans le modèle.
3. Vitesse de défilement plafonnée à **2 500 px/s** par défaut (`QB:qplatformtheme.cpp:705-708`) : régler `maximumFlickVelocity`/`flickDeceleration`, ou piloter `contentY` ; sinon le banc L1 mesure le plafond de Qt, pas le rendu.
4. `dataChanged` **une ligne à la fois** à haut débit ⇒ O(\|cache\|) + O(#en attente) par appel (§6) : regrouper en plage par frame (idiome recommandé : `performance.qdoc:669-686` « batch up backend operations »), ne pas émettre depuis le fil producteur.
5. `ListModel`/tableaux JS pour 100 k–10 M lignes : explicitement déconseillé (`performance.qdoc:688-692`) ; `dynamicRoles` à éviter (l.709-719) ; utiliser un `QAbstractListModel` C++ avec `rowCount()` O(1) et données calculées à la demande (`fnv(i)`).
6. `Text` : régler `textFormat: Text.PlainText` (sinon `mightBeRichText` à chaque changement, `ITEMS:qquicktext.cpp:1846` ; doc `performance.qdoc:539-546`) ; fixer largeur/hauteur pour éviter le recalcul de taille implicite ; ne **pas** mettre `Text.text` à chaque frame par `setText` manuel si une liaison existe (spec U2) mais ne pas non plus créer de liaison JS lourde : une expression typée simple compilée.
7. `TextEdit` gros document : le coût de première mise en page est inévitable (§5) ; **ne pas** appeler `text` en lecture (`QQuickTextEdit::text()` reconstruit une `QString` du document) dans une liaison ; `textFormat: PlainText`, `readOnly: true`, dans un `Flickable` ; ne pas activer `wrapMode` si non voulu (relayout à chaque largeur).
8. Peinture native : préférer **`QQuickPaintedItem` (C++, API publique)** ou un `QSGRenderNode` (`QPainter` via `PainterResource`) pour G1–G3 ; le `Canvas` QML coûte un appel JS par primitive + rejeu + texture par frame (doc recommande `Canvas.Threaded`/`Cooperative` pour décharger) ; **ne pas** créer un `Rectangle` par forme sauf à le documenter (spec §5 G).
9. Ombres/flous/`MultiEffect`/`ShaderEffect` : **non rendus** en software ; ne pas les laisser dans la scène (coût sans rendu : `performance.qdoc:736`, `performance.qdoc:853-863`, `adaptations.qdoc:115-118`) ; déclarer `unsupported` ou une approximation explicitement non équivalente (sprite pré-flouté).
10. Opacité de groupe : `opacity: 0.5` n'est pas un groupe en software ; utiliser `layer.enabled: true` pour un vrai groupe — mais chaque groupe plein cadre coûte un `QPixmap` plein cadre (§1.4).
11. `QQuickPaintedItem` : `setRenderTarget(Image)` (défaut) ; **appeler `update(rect)`** avec le rect sale pour ne repeindre que la zone utile ; `FramebufferObject` ne sert pas en software.
12. `QT_QPA_UPDATE_IDLE_TIME=0` pour le benchmark bas niveau (doc officielle, `scenegraph.qdoc:447-451`) ; `QSG_RENDER_TIMING` est **inopérant** : utiliser `QT_LOGGING_RULES` (§10.1).
13. Ne **pas** forcer des redessins par `QQuickWindow::update()` à chaque `frameSwapped` sans animation si l'on veut mesurer un coût de rendu stable (le tick de 16 ms des animations existe déjà) ; la cadence 60 Hz imposée par `QTimer::singleShot(PreciseTimer)` est publique et correcte (`V2`).
14. Images : `asynchronous: true` + `sourceSize` explicite, ou `QQuickAsyncImageProvider` + `QThreadPool` (`performance.qdoc:558-576`) ; ne pas décoder dans le fil GUI pendant la mesure ; `smooth: false` est une option valide **seulement** si la spec du contenu l'autorise (équité : pas de réduction de qualité visible).
15. FFI : appeler les fonctions C depuis des **fils C++**, pas depuis du JS ; pour F2 documenter la coalescence (lot par frame) ; ne pas utiliser `Qt::BlockingQueuedConnection` (gèle le producteur, §9).
16. Redimensionnement (U1) : préférer `anchors.fill`/positions fixes à des liaisons `width: parent.width` (`performance.qdoc:593-640`) ; utiliser `visible: false`/`Loader` pour les arbres hors écran **uniquement si la spec le permet** (U1 exige l'arbre complet).
17. Calcul du carré de latence : changer la couleur **dans le gestionnaire `Keys.onPressed`** après l'application à l'éditeur ; un `Rectangle` opaque, sans animation (`Behavior`) ni opacité.
18. Pas d'API privée (`QSGSoftware*`, `QQuickItemPrivate`, `QAnimationDriver` interne) ni de `qputenv("QSG_…")` caché : les variables d'environnement sont documentées dans `NOTES`.

**Faux amis de mesure**

- `frame_ms` par `frameSwapped` ne compte pas le temps de Xvfb (§1.1) ; à documenter dans `notes` ; `ops.ui_stall_ms_max` par `QTimer` de 4 ms **est** mesurable (API publique).
- La 1ʳᵉ frame d'un `TextEdit` volumineux est précédée d'un long gel : `ops.setup_ms` doit inclure `layout_ms`.
- Les frames sans changement de contenu ne sont pas rendues (aucun `frameSwapped`) : un scénario idle montre 0 frame (comportement normal).
- Le `QQuickWindow::color` par défaut est blanc opaque : fond = nœud opaque (`SW:qsgabstractsoftwarerenderer.cpp:99-102`).
