## 1. Architecture de rendu : de « une propriété change » à « un pixel est écrit »

### 1.1 Modèle : scène retenue (retained), double arbre client/serveur, deux threads
Avalonia 12 n'a plus de scène « immédiate » : chaque `Visual` possède un `CompositionVisual` côté client (thread UI) et un objet serveur miroir (`ServerCompositionVisual`) côté « render thread » (`AB/Visual.Composition.cs:22-45`, `RC/Server/ServerCompositionVisual/`). Les changements transitent par des **batches** sérialisés (`RC/Compositor.cs:123-190` `CommitCore`, `RC/Server/ServerCompositor.cs:77-134` `ApplyPendingBatches`).

Chaîne complète, propriété → pixel :
1. `SetValue` → `ValueStore` → `OnPropertyChanged`. Les propriétés `AffectsRender` de `Visual` (`Bounds, Clip, ClipToBounds, IsVisible, Opacity, OpacityMask, Effect, HasMirrorTransform`, `AB/Visual.cs:141-150`) et celles déclarées `AffectsRender<T>` par un contrôle appellent `Visual.InvalidateVisual()` (`AB/Visual.cs:418-421`) → `CompositingRenderer.AddDirty(visual)` (`RC/CompositingRenderer.cs:83-100`, ajout dans un `HashSet<Visual>`) → `QueueUpdate` → `Compositor.RequestCompositionUpdate` → `RequestCommitAsync` (`RC/Compositor.cs:90-107`) → `MediaContext.CommitRequested` (planificateur UI).
2. `MediaContext.ScheduleRender` (`AB/Media/MediaContext.cs:76-107`) poste une `DispatcherOperation` de priorité `Render` sur le dispatcher UI ; `RenderCore` (`:134-160`) fait : pulse de l'horloge d'animation, callbacks « invoke on render » (c'est là qu'a lieu **la passe de mise en page**, voir §4), puis `CommitCompositorsWithThrottling` (`AB/Media/MediaContext.Compositor.cs:64-81`).
3. Pendant `CompositingRenderer.UpdateCore` (`RC/CompositingRenderer.cs:165-204`) : pour **chaque visual sale**, `SynchronizeCompositionProperties()` réécrit ~12 propriétés (offset, taille, visible, opacité, clip, transform…, `AB/Visual.Composition.cs:129-190`, avec un `TODO: dirty mask` explicite `:135`) puis `visual.Render(_recorder)` ré-enregistre **toute la liste de dessin de ce visual** (pas des enfants) dans un flux d'opcodes `RenderDataStream` (`RC/Drawing/RenderDataDrawingContext.cs`). Le flux est attaché à `CompositionDrawListVisual.DrawList`.
4. `Compositor.CommitCore` sérialise les objets modifiés dans un `BatchStream` et fait `ServerCompositor.EnqueueBatch` (`RC/Server/ServerCompositor.cs:66-71`, `lock` + `Wakeup()` de la boucle de rendu).
5. Côté serveur (`ServerCompositor.RenderCore`, `:251-291`) : `ApplyPendingBatches` → `NotifyBatchesProcessed` → animations serveur (`Animations.Process`) → passes `RecomputeOwnProperties`, adorners → pour chaque cible : `ServerCompositionTarget.Update` (passe de mise à jour des bornes/zones sales) puis `Render`.
6. `ServerCompositionTarget.Render` (`RC/Server/ServerCompositionTarget.cs:140-286`) : crée (ou réutilise) le `IRenderTarget`, décide « couche intermédiaire ou non » (`:198-201`), `CreateDrawingContext`, redessine sous clip des zones sales, `Dispose` du contexte → **blit** du framebuffer.
7. Le blit logiciel X11 : `X11FramebufferSurface.Blit` (`X11/X11FramebufferSurface.cs:23-50`) : `XCreateGC` + **`XPutImage` de la fenêtre entière** (largeur×hauteur du framebuffer, `:41`) + `XSync(display, true)` (`:43`) puis `XFreeGC`. Ce blit est déclenché par la libération du `ILockedFramebuffer` (`AB/Platform/RetainedFramebuffer.cs:38-47`).

### 1.2 Zones sales (damage) — le point faible du chemin logiciel par défaut
- La passe `Update` (côté serveur) marque et propage « sale dans le sous-arbre » ; elle **ne descend que dans les sous-arbres sales** (`RC/Server/ServerCompositionVisual/ServerCompositionVisual.Update.cs:64` : `visitChildren = node._isDirtyForRenderInSubgraph || node._needsBoundingBoxUpdate`). Coût de mise à jour ∝ nombre de visuals modifiés, pas ∝ taille de l'arbre.
- Le suivi des rectangles est fixé à la construction de la cible : `SingleDirtyRectTracker` par défaut, c'est-à-dire **l'union de tous les rectangles sales en une seule boîte englobante** (`RC/Server/ServerCompositionTarget.cs:65-75` ; `RC/Server/DirtyRects/SingleDirtyRectTracker.cs:11-50`). Le suivi multi-rectangles/région (`MultiDirtyRectTracker`, max 8, `RegionDirtyRectTracker`) n'est activé **que si** `CompositionOptions.UseRegionDirtyRectClipping == true` (`:65` ; `RC/CompositionOptions.cs:11`), option **publique** mais **nulle par défaut** (aucune affectation dans `src/` : recherche `UseRegionDirtyRectClipping` → seulement la lecture `ServerCompositionTarget.cs:65`). `SK/PlatformRenderInterface.cs:59` : `SupportsRegions => true`.
- Conséquence : deux petits changements aux deux coins de la fenêtre ⇒ repeinture quasi totale. Dans nos bancs, le **carré de latence 200×200 en (100,100)** (union avec tout contenu animé) et tout défilement de liste (viewport entier) donnent une zone sale ≈ plein cadre.

### 1.3 Passes de rendu et chemin « couche » (CPU, X11 par défaut)
- `needLayer = overlays.RequireLayer || !(RetainsPreviousFrameContents && IsSuitableForDirectRendering)` (`ServerCompositionTarget.cs:198-201`).
- Pour X11 logiciel : `X11FramebufferSurface.CreateFramebufferRenderTarget()` renvoie `FuncFramebufferRenderTarget(Lock, _retain)` (`X11/X11FramebufferSurface.cs:71`), avec `_retain = X11PlatformOptions.UseRetainedFramebuffer ?? false` (`X11/X11Window.cs:239-240`, `X11/X11Platform.cs:507`). **Par défaut `_retain=false`** ⇒ `RetainsPreviousFrameContents=false` (`SK/FramebufferRenderTarget.cs:43-48`) ⇒ **`needLayer=true`** : une surface Skia raster `PixelSize` intermédiaire (`ServerCompositionTarget.cs:227-233`), dessin des zones sales dedans (`:257-260`), `Clear(Transparent)` du framebuffer, `layer.Blit` (copie plein cadre, `:262-270`, `SK/SurfaceRenderTarget.cs:138-154`), puis `XPutImage` plein cadre. Après chaque Blit le framebuffer est **détruit** (`X11FramebufferSurface.cs:45-49`) puis **réalloué** au `Lock` suivant (`:59-65`, `RetainedFramebuffer` = `UnmanagedBlob` de L×H×4 octets) ; `properties = FramebufferLockProperties(framebufferValid)` est donc toujours faux ⇒ `_fullRedrawRequested`/`fullRedraw` (`ServerCompositionTarget.cs:241-245`).
- Avec `UseRetainedFramebuffer=true` : plus de couche, plus de réallocation, dessin direct des zones sales dans un tampon persistant (l'option est documentée comme « saving a blit », `X11/X11Platform.cs:500-507`) ; **le `XPutImage` reste plein cadre** (`:41`).
- Coût fixe estimé par frame dessinée sous 1280×720×4 = 3,69 Mo [inféré] : (couche : effacement 3,7 Mo) + (blit couche→framebuffer : lecture+écriture) + `XPutImage` (copie utilisateur→noyau→Xvfb→framebuffer Xvfb, via socket unix, **sans MIT-SHM**) + attente `XSync` synchrone. Ordre de grandeur **3–8 ms/frame et une fraction de cœur dans le processus Xvfb** (le CPU Xvfb n'est pas dans le processus de l'app : à comptabiliser par le harnais).
- Les rendus GLX/EGL/Vulkan sont tentés avant le logiciel : `RenderingMode` par défaut `{Glx, Software}` (`X11/X11Platform.cs:410-413`) ; `GlxRendererBlacklist` contient `"llvmpipe"` (`:482`), donc sous Xvfb sans GLX réel on retombe sur Software (à vérifier à l'exécution, `X11/X11Platform.cs:218-286`). Pour forcer et rendre le choix explicite : `X11PlatformOptions.RenderingMode = [Software]`.

### 1.5 Qui fait quoi, sur quel thread
- **Thread UI** (boucle epoll X11, `X11/Dispatching/X11PlatformThreading.cs:117-165`) : événements X11 + entrées (traitées **en ligne** dans la boucle : `EventGrouperDispatchQueue`, `:155-160`, pas via la file du dispatcher), dispatcher, styles, mise en page, liaisons, enregistrement des listes de dessin (`Visual.Render`), commit des batches, horloge d'animation.
- **Thread de rendu** (créé à la demande par `SleepLoopRenderTimer`, `AB/Rendering/SleepLoopRenderTimer.cs:42-46`, non nommé, `IsBackground=true`) : applique les batches, passe Update, rastérise (Skia), `XPutImage`. Choix par `X11PlatformOptions.ShouldRenderOnUIThread` (défaut `false`, `X11/X11Platform.cs:82-84, 465`) → sinon `UiThreadRenderTimer` (un `DispatcherTimer` sur le thread UI, `AB/Rendering/UiThreadRenderTimer.cs`). Les calculs de l'UI et du rendu **s'exécutent en pipeline** (voir §2).
- **Verrou** : `ServerCompositor.RenderReentrancySafe` prend `lock(_lock)` (`ServerCompositor.cs:209-230`) ; les rendus synchrones (`Paint`/`Expose`/redimensionnement) font attendre le thread UI jusqu'à `batch.Rendered` (`AB/Media/MediaContext.Compositor.cs:95-118`, `CompositingRenderer.Paint` `RC/CompositingRenderer.cs:~232-240`).
- **Parcours de rendu** : `ServerCompositionVisual.Render` marche l'arbre serveur ; pour chaque visual : test d'intersection de la boîte du sous-arbre avec clip et zone sale (`ServerCompositionVisual.Render.cs:84-87`) → saut du sous-arbre si hors zone. **Pas d'index spatial** : un conteneur qui intersecte visite tous ses enfants (coût ∝ nombre d'enfants des conteneurs visibles, pas ∝ taille totale).
- **Mutations par frame** : toute mutation d'un visual (propriété `AffectsRender`) ⇒ ré-enregistrement de sa liste de dessin entière + écriture de ses ~12 propriétés + sérialisation batch. Il n'y a pas de dessin « mutation seule » sans passer par ce chemin, sauf **animations de composition** (`CompositionAnimation`, évaluées côté serveur : `RC/Animations/`, `RC/Server/ServerCompositorAnimations.cs`, API `ElementComposition.GetElementVisual` public `RC/ElementCompositionPreview.cs:16`).
- **`SceneInvalidated`** : après chaque batch « Rendered », un `Dispatcher.UIThread.Post(..., Input)` est ajouté (`RC/CompositingRenderer.cs:195-207`) pour rafraîchir le hit-testing (survol) : une tâche UI supplémentaire par frame.

### 1.6 Canvas natif (graphisme CPU)
- `DrawingContext` public (`AB/Media/DrawingContext.cs`) : `DrawRectangle/DrawEllipse/DrawLine/DrawGeometry/DrawImage/DrawGlyphRun/Custom/Push*`.
- `Control.Render(DrawingContext)` est ré-invoqué à chaque `InvalidateVisual` et **enregistre** les opérations (retained) ; il ne dessine pas directement.
- **Brosses mutables** : `RenderDataDrawingContext.AddResource` (`RC/Drawing/RenderDataDrawingContext.cs:40-62`) court-circuite seulement `IImmutableBrush`, `ImmutablePen`, `ImmutableTransform` (`:46-48`) ; toute `SolidColorBrush`/`Pen` **mutable** passe par `HashSet` + `AddRefOnCompositor` + ressource serveur. En mode « N formes par frame », préférer `Brushes.*`/`ImmutableSolidColorBrush`/`ImmutablePen` (voir §12).
- `ICustomDrawOperation` (`AB/Rendering/SceneGraph/CustomDrawOperation.cs`) : exécuté sur le **thread de rendu** (`RC/Drawing/RenderDataStream.Replay.cs:57-58`), reçoit un `ImmediateDrawingContext` ; l'API Skia directe passe par `ISkiaSharpApiLeaseFeature` / `ISkiaSharpApiLease` (`SK/ISkiaSharpApiLeaseFeature.cs`, marqués `[Unstable]` : autorisés par la spec s'ils sont documentés en `NOTES`). `Bounds` de l'opération alimente les bornes du visual et donc la zone sale.

## 2. Boucle d'événements et cadence

- **Dispatcher** : un `Dispatcher` par thread, UI = `Dispatcher.UIThread`, implémentation X11 = `X11PlatformThreading` (epoll sur le fd X11 + pipe de signal + minuteur) sauf `UseGLibMainLoop` (`X11/X11Platform.cs:89-92`). Boucle `RunLoop` : timer → flush X → `epoll_wait(timeout=prochain minuteur ms)` → `CheckSignaled()` (jobs du dispatcher) → `DispatchX11Events` → file des entrées groupées (`X11/Dispatching/X11PlatformThreading.cs:117-165`). Granularité des minuteurs : **1 ms** (`Math.Max(1, …)`, `:139`).
- **Priorités** (plus grand = plus prioritaire) : `Input=-1 < Default=0 < Loaded < UiThreadRender < AfterRender < Render < BeforeRender < AsyncRenderTargetResize < DataBind < Normal < Send` (`AB/Threading/DispatcherPriority.cs:25-127`). `Post(action)` sans priorité = `Default` (`AB/Threading/Dispatcher.Invoke.cs:616-620`, `default(DispatcherPriority)` = 0).
- **Starvation d'entrée** : `ExecuteJobsCore` exécute en boucle **tout job de priorité > Input sans jamais rendre la main** tant que la file n'est pas vide (`AB/Threading/Dispatcher.Queue.cs:159-175` : « We don't stop for executing jobs queued with >Input priority ») ; seuls les jobs `≤ Input` cèdent devant `HasPendingInput` (`:176-185`, `X11/Dispatching/X11PlatformThreading.cs:201-203`). Un producteur de fond qui poste en continu à `Default`+ peut donc affamer la boucle X11 (entrées, Expose, redimensionnement) tant que le producteur est plus rapide que la consommation.
- **Planification d'une frame à 60 Hz sous X11/Xvfb** :
  1. Minuteur : `SleepLoopRenderTimer(DefaultFps=60)` (`X11/X11Platform.cs:33, 82-84`) ; `DesiredFps = max(60, taux XRandR)` (`X11/Screens/X11Screens.cs:21-22`, `X11/X11Platform.cs:111-114`) ; sous Xvfb sans mode CRTC : `DefaultFps` (60) (`X11/Screens/X11Screen.Providers.cs:193-205`). **Ce n'est pas un vsync** : c'est un fil qui dort (`AB/Rendering/SleepLoopRenderTimer.cs:62-79`). Le sommeil est `AutoResetEvent.WaitOne(TimeSpan)` seulement si le reste > 1 ms (`:73-74`) ; `WaitOne(TimeSpan)` a une granularité en millisecondes entières [inféré, API .NET] ⇒ période effective ≈ 16–17 ms, non verrouillée à 16,667 ms (≈ 61–62 Hz possible, comme Slint à 62,5 Hz dans la spec).
  2. `DefaultRenderLoop.TimerTick` (`AB/Rendering/RenderLoop.cs:123-182`) appelle `ServerCompositor.Render()` ; tant qu'il y a des animations serveur **ou** moins de 10 ticks depuis le dernier commit (`CommitGraceTicks=10`, `ServerCompositor.cs:49, 280`) la boucle redemande un tick ; sinon le minuteur s'arrête (`_timer.Tick = null`) ⇒ **CPU ≈ 0 à l'arrêt** (scénario `idle`).
  3. Réveil : `EnqueueBatch` → `_renderLoop.Wakeup()` (`ServerCompositor.cs:66-71`, `RenderLoop.cs:107-121`) ; si le minuteur était arrêté, le fil de rendu repart sans attendre le prochain intervalle (`lastTick` ancien ⇒ `timeTillNextTick<0`).
  4. **Coalescence** : `RenderLoop.TimerTick` est protégé par `_inTick` (un seul tick à la fois). Les invalidations UI se regroupent dans `_dirty`/`_objectSerializationQueue` jusqu'au commit ; `MediaContext.ScheduleRender` ne crée qu'une `DispatcherOperation` à la fois (`_nextRenderOp != null` ⇒ retour, `MediaContext.cs:76-84`).
  5. **Contre-pression UI→rendu** : l'UI **ne commit pas** un nouveau batch tant que le précédent n'est pas « Processed » (= appliqué par le thread de rendu en début de tick) (`MediaContext.Compositor.cs:64-70`) ; elle ne dépend pas de « Rendered ». La fin de traitement revient par `Dispatcher.Post(..., Send)` (`:41-61`). Le pipeline est donc à 2 étages : l'UI prépare la frame N+1 pendant que le thread de rendu rastérise la frame N. Débit = `max(travail UI, rastérisation+XPutImage, ≈16,3 ms)`.
  6. **Animations UI** : sans activité de rendu, un `DispatcherTimer(Render)` de 16 ms relance `ScheduleRender` (`MediaContext.cs:30-36, 47-51`). `MediaContext.RenderCore` appelle `_clock.Pulse` ; `Pulse` copie les observateurs `ToArray()` **à chaque frame** (`MediaContext.Clock.cs:61`).
  7. **Garde-fou d'entrée UI** : un marqueur d'`Input` est posté avec chaque rendu planifié et, si le marqueur n'a pas été traité depuis `InputStarvationTimeout`, le rendu suivant passe à priorité `Input` (`MediaContext.cs:88-107`).
- **Plafond de cadence** : `X11PlatformOptions` n'expose aucun réglage de FPS. `IRenderTimer`/`IRenderLoop` sont `[PrivateApi]` (`AB/Rendering/IRenderTimer.cs:6`, `IRenderLoop.cs:12`). Donc `BENCH_PACING=uncapped` n'est **pas obtenable par API publique** sous X11 : à déclarer `unsupported`/`ops.pacing="60"`. `ShouldRenderOnUIThread=true` change seulement le fil.
- **Redimensionnement** : le `ConfigureNotify` est posté à `AsyncRenderTargetResize` (priorité très haute) (`X11/X11Window.cs:690-712`) ; la fenêtre est resynchronisée par un rendu synchrone (`Paint` → `ImmediateRenderRequested` → attente `Rendered`, `MediaContext.Compositor.cs:95-129`) : la tempête de redimensionnement U1 est **entièrement sérialisée UI↔rendu**, sans recouvrement.

## 3. Moteur de propriétés / liaisons / réactivité

- **Objet** : chaque `AvaloniaObject` alloue un `ValueStore` dès la construction (`AB/AvaloniaObject.cs:37`), qui contient d'emblée une `List<ValueFrame>` (`AB/PropertyStore/ValueStore.cs:19`) et un dictionnaire d'`EffectiveValue` (`:21`). **Chaque propriété posée localement crée un objet `EffectiveValue<T>`** (classe scellée, `AB/PropertyStore/EffectiveValue`1.cs:16`, `ValueStore.cs:~940 AddEffectiveValue`). Lecture : `GetValue` « performance critical » (`ValueStore.cs:286-295`), recherche dans un dictionnaire spécialisé puis héritage (`TryGetInheritedValue`).
- **Coût d'un changement de propriété stylée** (`SetValue`, `AvaloniaObject.cs:313-352` → `ValueStore.SetValue` → `EffectiveValue<T>.SetAndRaiseCore` `EffectiveValue`1.cs:204-260`) : `VerifyAccess` (`AvaloniaObject.cs:126`), coercition éventuelle, comparaison `EqualityComparer<T>.Default`, puis `NotifyValueChanged` (`EffectiveValue`1.cs:305-311`) : `PropertyNotifying` (struct), **allocation d'un `AvaloniaPropertyChangedEventArgs<T>` (classe)** à chaque changement effectif (`AvaloniaObject.cs:732`), appels `OnPropertyChangedCore` → `property.NotifyChanged` (handlers de classe : `AffectsRender/AffectsMeasure` en font partie) → événement `PropertyChanged` et, **seulement s'il y a un abonné INPC**, un `PropertyChangedEventArgs` supplémentaire (`:746`). Propriétés héritées : `OnInheritedEffectiveValueChanged` descend dans **tous** les enfants (`ValueStore.cs:980-1006`).
- **Liaisons** : `BindingExpression` (`AB/Data/Core/BindingExpression.cs`) = chaîne de nœuds (`ExpressionNode`), `OnNodeValueChanged` → `ConvertAndPublishValue` (`:193-230, 449-498`) → `PublishValue` → `SetValue` de la propriété cible au niveau de priorité de liaison. Source INPC : abonnement par `WeakEvents.ThreadSafePropertyChanged` (`AB/Data/Core/Plugins/InpcPropertyAccessorPlugin.cs:188-191`) dont le gestionnaire **poste sur le thread UI via `Dispatcher.UIThread.Post(...)` si l'événement est levé hors thread UI** (`AB/Utilities/WeakEvents.cs:27-48` : une `DispatcherOperation` + fermeture par événement).
- **AOT/réflexion** : `Binding`/`ReflectionBinding` sont marqués `[RequiresUnreferencedCode]`/`[RequiresDynamicCode]` (`AB/Data/ReflectionBinding.cs:19-20`, message « Consider using CompiledBindings instead », `AB/Diagnostics/TrimmingMessages.cs:11-12`). Voies AOT-sûres en code (F#, sans XAML) : `CompiledBinding.Create<TIn,TOut>(Expression<Func<TIn,TOut>>, …)` (public, `AB/Data/CompiledBinding.cs:88-117`, coût de construction : visiteur d'expression à l'exécution), `CompiledBindingPathBuilder` (`AB/Data/CompiledBindingPath.cs:103-227`, fabriques d'accesseurs explicites) ou liaison sur `IObservable` (`AvaloniaObject.Bind(prop, IObservable<T>, priority)`, `AvaloniaObject.cs:~465-583` → `ValueStore.AddBinding` `:49-140`).
- **Coût de N liaisons** [inféré] : mémoire ≈ `BindingExpression` + nœuds (+ `WeakReference`, abonnement faible) par liaison, soit plusieurs centaines d'octets ; **chaque mise à jour** = lecture de la source, conversion éventuelle (boxing), `string.Format` si `StringFormat`, `SetValue` (alloc `EventArgs`), puis effets en cascade (`InvalidateMeasure`/`InvalidateVisual`). Avec un `TextBlock.Text` lié : le passage par `InvalidateTextLayout` (§5) domine.
- **Dépendances** : pas de graphe de dépendances calculé ; la propagation est événementielle (notifications synchrones, dans le thread UI uniquement : `VerifyAccess`).

## 4. Mise en page

- **Algorithme** : mise en page à deux phases `Measure` puis `Arrange` récursives, **invalidation ciblée** (`InvalidateMeasure` marque le contrôle `!IsMeasureValid && !IsArrangeValid`, l'enfile dans le `LayoutManager`, appelle `InvalidateVisual`, `AB/Layout/Layoutable.cs:443-456`). `Measure(availableSize)` ne recalcule que si `!IsMeasureValid || _previousMeasure != availableSize` (`:374`) ; `Arrange` idem (`:415-438`, `_previousArrange != rect`). Si la taille désirée change, le parent est notifié (`:406`) et se ré-invalide.
- **`LayoutManager`** (`AB/Layout/LayoutManager.cs`) : files `_toMeasure`/`_toArrange` (`LayoutQueue`), **une passe par frame** exécutée comme callback « avant rendu » de `MediaContext` (`QueueLayoutPass` → `BeginInvokeOnRender`, `:348-353`), jusqu'à `MaxPasses=10` itérations imbriquées (`:23, 116-170, 237-249`). La mesure d'un contrôle sale **remonte récursivement** jusqu'à la racine pour mesurer les ancêtres d'abord (`Measure(parent)` récursif, `:286-309` : commentaire explicite « shown by benchmarks to be the fastest ») ⇒ profondeur d'arbre = profondeur de pile.
- **Coût par élément** [inféré, lecture de `MeasureCore` `AB/Layout/Layoutable.cs:544-632`] : lecture de `Margin`, `UseLayoutRounding`, `Width/MinWidth/MaxWidth/Height/…` (6 propriétés via `MinMax`, `AB/Layout/MinMax.cs:12-16`), `ApplyStyling()` + `ApplyTemplate()`, requête de conteneur (`Container.GetQueryProvider`), `MeasureOverride`, arrondi de layout. `GetLayoutRoot()` est O(1) (`AB/VisualTree/VisualExtensions.cs:459`, pointeur `PresentationSource`). Ordre de grandeur **1,5–4 µs/élément/passe** pour un contrôle simple ; ×2 (mesure+arrangement).
- **Redimensionnement / grands arbres** : si la contrainte de la racine change, chaque contrôle dont la taille disponible dépend de la fenêtre se remesure (Grid/StackPanel avec enfants `Stretch`) ; ceux à taille fixe coupent la propagation. Pas de parallélisme (tout sur le thread UI, `Dispatcher.UIThread.VerifyAccess()` partout). Les passes sont instrumentées (`Diagnostic.BeginLayoutMeasurePass`, `LayoutManager.cs:~253-266`).
- **Conseil officiel** : arbre « plat », layout = 2 passes par élément (`docs.avaloniaui.net/docs/guides/development-guides/improving-performance`, lue le 2026-10-26, section « Optimize your visual tree structure »).
- **Banc officiel** : `TB/Layout/Measure.cs`, `TB/Layout/ControlsBenchmark.cs` (création + layout d'un `Calendar`), `TB/Traversal/VisualTreeTraversal.cs`.

## 5. Texte

- **Pile** : `TextBlock` (contrôle) → `TextLayout` (`AB/Media/TextFormatting/TextLayout.cs`) → `TextFormatterImpl` → **`TextShaper` → `HarfBuzzTextShaper`** (`HB/HarfBuzzTextShaper.cs:23-117`, `font.Shape(buffer, features)` `:64`, tampon `Buffer` `[ThreadStatic]` réutilisé `:19, 41`, `Language` mise en cache `:21`) → `GlyphRun` → `GlyphRunImpl` Skia (`SK/GlyphRunImpl.cs`) ; Unicode/bidi/segmentation en C# géré (`AB/Media/TextFormatting/Unicode/*`, tables trie). HarfBuzzSharp 8.3.1.3 (natif).
- **Cache** : (a) `TextRunCache` optionnel par `TextLayout` (`AB/Media/TextFormatting/TextRunCache.cs`, utilisé par `TextBlock`, `TextBlock.cs:718`), conserve les runs formés pour un texte/contrainte identique, **invalidé à chaque changement de `Text`** (`InvalidateTextLayout`, `TextBlock.cs:724-731`) ; (b) `SKTextBlob` par `GlyphRunImpl`/`TextOptions` (`GlyphRunImpl.cs:116`) ; (c) cache de glyphes rasterisés de Skia. **Aucun cache de mise en forme entre textes différents** : un compteur qui change à chaque frame refait mesure + shaping + création de `GlyphRun` + `GlyphRunImpl`.
- **Création d'un `GlyphRunImpl`** : `new SKFont` pour calculer les largeurs/bornes de glyphes (`SK/GlyphRunImpl.cs:56-69`) ; un `SKTextBlob` est construit à la première peinture par `TextOptions`.
- **Changement de texte** (`TextBlock.OnPropertyChanged`, `TextBlock.cs:923-1005`) : `InvalidateTextLayout` ⇒ `DisposeTextLayout` + `InvalidateVisual` + `InvalidateMeasure` (`:724-731`) ⇒ passe de mise en page (mesure, éventuellement ré-arrangement du parent), ré-enregistrement, commit batch. Chemin complet par étiquette et par frame : environ 20–50 µs [inféré].
- **Gros documents** : `TextLayout.CreateTextLines` met en forme **toutes** les lignes en boucle jusqu'à la fin du texte, sauf `MaxHeight`/`MaxLines` (`AB/Media/TextFormatting/TextLayout.cs:557-640`) ; `TextLayout.Draw` **dessine toutes les lignes sans cull de viewport** (`:295-310`, `TextLineImpl.Draw` `AB/Media/TextFormatting/TextLineImpl.cs:103-123`). Donc un `TextBlock`/`SelectableTextBlock`/`TextBox` (`AC/Presenters/TextPresenter.cs:416` `TextLayout.Draw`) portant 1–100 Mo : formatage O(taille) à chaque invalidation de la mise en page ou du texte, mémoire O(taille × ~100 o/car) [inféré], et un enregistrement O(lignes) par `InvalidateVisual` (la rastérisation Skia rejette hors-clip les blobs mais l'enregistrement/les appels natifs restent O(lignes)). Le défilement d'un tel contrôle (via `ScrollViewer`) ne re-formate pas mais **rejoue toute la liste de dessin** à chaque frame.
- **Édition** (`TextBox`) : le texte est une `string` immuable ; chaque frappe = copie O(n) de la chaîne + invalidation complète du `TextLayout` du `TextPresenter` (`AC/Presenters/TextPresenter.cs:641-658`). `UndoRedoHelper` conserve par défaut **10 états contenant chacun la chaîne entière** (`AC/Utils/UndoRedoHelper.cs:7`, `AC/TextBox.cs:346-358`) ⇒ jusqu'à 10× la taille du document en mémoire. Un document de 1 Mo ⇒ latence de frappe dominée par le re-formatage complet.
- **Bidi/CJK/emoji** : bidi UAX#9 et segmentation de lignes implémentés en C# (`AB/Media/TextFormatting/Unicode/BiDiAlgorithm.cs`, `LineBreakEnumerator.cs`, `GraphemeBreak.cs`) ; repli de police par `FontManager` (`AB/Media/FontManager.cs`, `FontFallbackScriptHints.cs`) + `FontManagerImpl` Skia (fontconfig sous Linux, **[Skia-doc]**) ⇒ des polices CJK/emoji/arabe doivent être présentes sur la VM de test, sinon glyphes manquants (`.notdef`) : à vérifier avant les bancs T4.
- **Bancs officiels** : `TB/Text/HugeTextLayout.cs` (construction de `TextLayout` multi-paragraphes avec Wrap/Trim, + emoji), `TextLayoutProfile.cs`, `TextRunCacheBenchmark.cs`, `ShapedBufferOps.cs`, `Unicode*Benchmark.cs`, `CodepointBenchmark.cs` ; `TB/Program.cs:~24` expose un harnais de profil `--profile-textlayout` (dotnet-trace).

## 6. Listes / virtualisation

- **Composant officiel** : `ItemsControl`/`ListBox` + `VirtualizingStackPanel` (`AC/VirtualizingStackPanel.cs`, 1492 lignes). `ItemsRepeater` n'existe pas dans les dossiers lus (WinUI) ; `TreeDataGrid` (hors dépôt) est le composant recommandé par la doc pour les gros jeux, **désormais sous Avalonia Pro** (`improving-performance`, encart « maintained as part of Avalonia Pro as of October 2025 ») : à ne pas utiliser pour l'équité.
- **Source de données** : `ItemsSourceView.SetSource` (`AC/ItemsSourceView.cs:267-283`) : une `IList` est utilisée telle quelle (aucune copie, `:276`) ; une collection qui implémente `INotifyCollectionChanged` **sans** `IList` est refusée (`:277-279`) ; toute autre `IEnumerable` est **copiée dans `List<object>`** (`:280-282`, boxing). Une `IList` « virtuelle » (indexeur calculé) évite toute matérialisation de 10 M d'éléments.
- **Virtualisation** : `MeasureOverride` (`VirtualizingStackPanel.cs:188-240`) calcule un viewport (`CalculateMeasureViewport`), réalise/recycle uniquement les conteneurs visibles (`RealizeElements`, `RecycleElementsBefore/After`), échange deux `RealizedStackElements` (`:227`). Recyclage par clé de template dans un `Dictionary<object, Stack<Control>>` (`:78, 1096-1125, 1211-1222`).
- **Hauteurs variables** : la taille d'un item n'est connue qu'une fois réalisé ; pour les autres, **estimation = moyenne des tailles réalisées** (`EstimateElementSizeU` `:806-832`, initiale 25 px `:73`) ; position d'un index non réalisé = `index × estimation` ou extrapolation depuis la zone réalisée (`GetOrEstimateElementU`, `:899-945`). Conséquences : l'étendue défilable (`Extent`) est une estimation qui bouge à mesure qu'on défile ; **`sum_heights` doit être calculé par l'appli**, pas lu dans le layout ; le défilement à vitesse pixel constante traverse des indices à vitesse non constante.
- **Pas de tampon par défaut** : `CacheLength` = 0.0 (`:58-60`, plage 0–2) ⇒ `_bufferFactor=0` (`:101`) ⇒ la « zone étendue » = le viewport ; `OnEffectiveViewportChanged` (`:1284-1330`) déclenche un **nouveau `MeasureOverride` dès que le viewport sort de la zone déjà réalisée**, soit quasiment à chaque frame en défilement continu. Un fling à 150 000 px/s (≈ 2 500 px/frame ≫ 720 px de viewport) est « disjoint » : `RecycleAllElements` puis réalisation complète à chaque frame (`:217-221`).
- **Coût d'un reset / insertion / `dataChanged`** : `OnItemsChanged` (`:344-385`) → `InvalidateMeasure` + `ItemsInserted/Removed/Replaced/Reset` sur les seuls éléments réalisés (O(réalisés)), plus la mise à jour d'index `UpdateElementIndex` pour les conteneurs suivants. Le coût O(N) est **côté collection** (insertion dans une `List`/`ObservableCollection` = déplacement mémoire O(N)), pas côté contrôle. Une modification de propriété d'un item (INPC) ne touche que les conteneurs réalisés liés à l'item (liaisons actives).
- **Création de conteneur** : `ItemsControl.PrepareContainerForItemOverride` (`AC/ItemsControl.cs:356-420`) pose `DataContext`/`Content`/`ItemTemplate` ; avec recyclage, une ligne recyclée **ré-évalue toutes ses liaisons** (nouveau `DataContext`) : coût ∝ nombre de liaisons par ligne (L2 : K×… liaisons).
- **Thread** : la collection doit être modifiée **sur le thread UI** (les `INotifyCollectionChanged` sont traités synchronement par `ItemsSourceView`/panneau ; pas de marshalling automatique) ; mises à jour de fond ⇒ file + `Dispatcher.UIThread` par lots.
- **Bancs officiels** : aucun banc de liste/virtualisation dans `tests/Avalonia.Benchmarks` (liste complète de dossiers : Animations, Base, Compositor, Data, Layout, Markup, Navigation, Rendering, Styling, Text, Themes, Traversal, Utilities, Visuals) : les chemins de liste ne sont **pas** reconnus comme chemins chauds mesurés par les mainteneurs.

## 8. Mémoire et modèle d'exécution (.NET 10 NativeAOT)

- **NativeAOT** : pas de JIT, pas de PGO dynamique, pas de chargement dynamique ni de `Reflection.Emit` (`learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/`, limitations, lue le 2026-10-26). Conséquence [inféré, connaissance générale .NET] : le code chaud n'est pas re-compilé en niveau 1 avec PGO (pas de dévirtualisation gardée) ; les appels d'interface et de délégués (très fréquents : `IDrawingContextImpl`, `EqualityComparer<T>.Default`, `IReadOnlyList<T>`) restent indirects. `Avalonia.Base/Controls/Skia/X11` sont compilés avec `IsAotCompatible=true`, `IsTrimmable=true`, analyseur de trimming activé (`build/TrimmingEnable.props` lu via raw, tag 12.1.4) et **`DisableRuntimeMarshalling`** (même fichier, 2ᵉ `ItemGroup`) ⇒ P/Invoke blittables.
- **Doc Avalonia AOT** (`docs.avaloniaui.net/docs/deployment/native-aot`, lue le 2026-10-26) : `PublishAot`, `IsAotCompatible`, `x:CompileBindings`, éviter les chargements dynamiques, racine de trimmer pour les assemblages à réflexion (`TrimmerRootAssembly`). Sans XAML (F# en code) les limites portent sur les liaisons (§3), les `TypeConverter` implicites (`TrimmingMessages.cs:5-9`) et toute API marquée `RequiresUnreferencedCode`.
- **Allocations par frame** (hot path lu) : `AvaloniaPropertyChangedEventArgs<T>` par changement (§3) ; `DispatcherOperation` + `ExecutionContext` capturé par `Post` (`AB/Threading/DispatcherOperation.cs:45-58`, `captureExecutionContext` vrai par défaut → `CulturePreservingExecutionContext.Capture()`) ; `HashSet`/closures dans l'enregistrement de brosses mutables ; LINQ + tableaux par dégradé (`DrawingContextImpl.cs:913-914`) ; `SKImageFilter` natif par ombre (`:334`) ; `_observers.ToArray()` par pulse (`MediaContext.Clock.cs:61`) ; `MediaContext.RenderCore` crée un `DispatcherOperation` par frame (`MediaContext.cs:103-105`). Le serveur utilise des pools (`CompositorPools`, `BatchStreamObjectPool/MemoryPool`, `RC/Server/CompositorPools.cs`) et `ArrayPool` ponctuels (`LayoutManager.cs:~364`).
- **GC** : GC .NET habituel (la configuration `System.GC.Concurrent`, `Server`, `RetainVM`, `ConserveMemory`, `GCHeapHardLimit` est documentée : `learn.microsoft.com/en-us/dotnet/core/runtime-config/garbage-collector`) ; lesquels sont honorés par le runtime NativeAOT n'est **pas vérifié ici**. Grande consommatrice d'objets (items de liste, `EffectiveValue`, `EventArgs`) : le GC éphémère gèle tous les threads managés (UI + rendu) pour les générations 0/1, ce qui cadre `ui_stall_ms_max` et p99 de frame. Instrumentation applicative : `GC.CollectionCount`, `GC.GetTotalPauseDuration`, `GC.GetTotalAllocatedBytes` (exigées par la spec §2).
- **Mémoire native** : pixmaps/couches Skia, framebuffer (`UnmanagedBlob`), `SKTextBlob`, cache de glyphes Skia (borné **[Skia-doc]**) ; non visible du GC ⇒ RSS ≠ tas géré (utiliser PSS du harnais).
- **Fuites typiques** : abonnements d'événements forts vers un objet de longue durée, `INotifyPropertyChanged` abonnés via `WeakEvent` (faibles, `WeakEvents.cs`) mais dont les listes ne sont nettoyées qu'à l'événement suivant ; `DispatcherTimer` non arrêtés (compteur exposé par la métrique `avalonia.ui.dispatcher.timer.count`, §10) ; ressources de brosses mutables `AddRefOnCompositor` non libérées avec le visual.
- **Taille d'un objet UI** [inféré] : `AvaloniaObject` + `ValueStore` + `List<ValueFrame>` + `EffectiveValue<T>` par propriété posée + objet `CompositionVisual` client + `ServerCompositionVisual` serveur (≈ 1,5–3 Ko par contrôle simple, à confirmer par mesure ; non lu : tailles réelles des champs).

## 9. FFI et fils

- **Appel du C** : `DllImport` blittable (assemblages Avalonia sous `DisableRuntimeMarshalling`, `X11/XLib.cs:28…` ≈ 185 `DllImport`, aucun `SuppressGCTransition` dans `src/Avalonia.X11` : recherche vide). Pour le cœur Rust du banc : `DllImport` blittable + `DirectPInvoke` (AOT, appel direct sans stub de résolution), `SuppressGCTransition` possible pour `core_noop`/`core_add` (**attention** : interdit pour tout appel susceptible de durer ou de rappeler du managé, donc pas pour `core_hash`/`core_fill`/`core_heavy` grands) ; tableaux passés par `fixed`/`Span` + pointeur (tampon créé une fois).
- **Rappels natif→managé** : `[UnmanagedCallersOnly]` (spec §3) ; premier appel d'un fil natif ⇒ attachement d'un fil managé (allocation `Thread`) ; chaque entrée coûte une transition GC inverse (**dizaines de ns** [inféré]).
- **Vers le thread UI** : `Dispatcher.UIThread.Post(Action, priority)` (`Dispatcher.Invoke.cs:616-620`) = allocation `DispatcherOperation` + capture de contexte d'exécution + `lock(InstanceLock)` + insertion dans la file à priorités (`InvokeAsyncImpl`, `:399-422`) + `RequestProcessing` → `Signal()` du pipe/epoll **une seule fois** tant que `_signaled` (`Dispatcher.Queue.cs:224-252`) ; `InvokeAsync<T>` ajoute un `TaskCompletionSource` (`DispatcherOperation.cs:362-368`). Idiome recommandé pour de gros débits : **file concurrente + un seul `Post` coalescé par frame** (aucune API de coalescence fournie par Avalonia).
- **Dans l'autre sens** : `Dispatcher.UIThread.InvokeAsync(...)` depuis l'UI = exécution synchrone si déjà sur le thread ; sinon enfilage. `AvaloniaSynchronizationContext` assure `await` sur l'UI (`AB/Threading/AvaloniaSynchronizationContext.cs`).
- **Fils de fond** : `Task.Run`/`ThreadPool` libres ; toute mutation `AvaloniaObject` hors UI lève (`VerifyAccess`, `AvaloniaObject.cs:126`). Les collections doivent donc être modifiées sur l'UI.
- **Rendu** : thread unique dédié (`SleepLoopRenderTimer`), contenu rastérisé par Skia **mono-thread** (aucune rastérisation parallèle de tuiles) : la 4ᵉ vCPU ne sert pas au rendu d'une fenêtre unique.

## 11. Points de rupture prédits (hypothèses falsifiables, datées 2026-10-26)

Hypothèses de base : Linux x64, 4 vCPU, Xvfb 1280×720, **rendu logiciel Skia**, `X11PlatformOptions.RenderingMode=[Software]`, NativeAOT, 60 Hz via `SleepLoopRenderTimer`. Les N_max sont des **ordres de grandeur** (fourchette [bas–haut]) pour une implémentation idiomatique optimisée (brosses immuables, `UseRetainedFramebuffer`, `CompiledBinding`/observables, coalescence) ; les valeurs « naïve » sont indiquées quand l'écart est le sujet. Les tailles de formes/contenus non précisées par la spec sont supposées ≈ 20×20 px (G1) et lignes de 24–44 px (L2).

### 11.2 Les cinq prédictions les plus risquées (à confronter en priorité)
1. **G1 gradient et shadow s'effondrent par un coût de gestion par dessin (shaders/`SKImageFilter` recréés)** : gradient ≈ ÷2–4, shadow ≈ ÷10–50 vs solid.
2. **F2 : le plafond naïf (`Post` par événement) ≈ 0,5 M évts/s et la famine des entrées X11** ; la coalescence explicite donne un ordre de grandeur de plus.
3. **G5 : par défaut, aucune couche (alpha multiplié par primitive)** : la « capacité » mesurée sera celle de G1 solid, avec un résultat visuel différent ; il faut activer explicitement `RequiresFullOpacityHandling` pour un groupe vrai.
4. **T1 : 10 Mo et plus cassent sur une seule `TextLayout`** (formatage total, pas de cull) ; **T3 à 1 Mo : latence par frappe de l'ordre de la seconde**.
5. **U1/resize : relayout complet O(N) ⇒ pas de 60 Hz pendant la tempête dès 10 k** ; et le coût fixe plein cadre (3–8 ms) réduit toute marge dès que la zone sale est large.

### 11.3 Préparation de l'interprétation des profils (`perf record -e cpu-clock -g`)
- Processus : thread UI = thread principal ; thread de rendu = fil anonyme créé par `SleepLoopRenderTimer` (`SleepLoopRenderTimer.cs:45`, pas de nom) ; fils GC et ThreadPool. Trier par `--sort tid`. **Xvfb est un autre processus** : `perf record -a` (ou `-p` Xvfb) pour compter `XPutImage` côté serveur (`memcpy`, `ProcPutImage`, `fbBlt`).
- Symboles : NativeAOT conserve les noms managés dans la table de symboles de l'exécutable si on **ne dépouille pas** (`StripSymbols=false`) ; les frames managées utilisent les pointeurs de frame (les piles `-g` par défaut `fp` devraient fonctionner pour le managé). `libSkiaSharp.so`/`libHarfBuzzSharp.so` : prévoir des adresses non résolues (binaires du paquet NuGet) ⇒ les attribuer par bibliothèque (`--sort dso`). **Non vérifié** : présence de pointeurs de frame dans Skia.
- Signatures attendues : repos = `epoll_wait` (UI), `pthread_cond_timedwait`/`futex` (rendu) ; plein cadre = `__memmove_avx_unaligned_erms`, `copy_user_enhanced_fast_string`, `unix_stream_sendmsg` (le `XPutImage`), `SkRasterPipeline`/blitters dans `libSkiaSharp.so` ; pauses GC = `gc_heap::*`, `WKS::gc_heap` (sous AOT le GC est lié au binaire) ; transition P/Invoke = stubs `RhpPInvoke*`/`RhpPInvokeReturn`.
- Métriques à lire avec le profil : `Avalonia.Diagnostic.Meter` (§10.1) pour répartir **UI (measure/arrange/render-recording)** vs **rendu (update/render)**.

## 12. Pièges d'implémentation (revue d'équité)

1. **Brosses/crayons mutables dans `Render`** (`new SolidColorBrush(..)`, `new Pen(..)` à chaque frame) : chaque dessin passe par `AddResource` (`HashSet` + `AddRefOnCompositor`, ressource serveur, `RenderDataDrawingContext.cs:40-62`). Utiliser `Brushes.*`, `ImmutableSolidColorBrush`, `ImmutablePen` (et les réutiliser). Un banc qui alloue des brosses mutables par forme mesurerait une erreur d'API, pas Avalonia.
2. **Une `Control` par forme** (G1/G2/G4/G5) au lieu d'un canvas : le brief l'interdit ; le canvas natif = un `Control` dont `Render` enregistre N opérations (ou `ICustomDrawOperation`).
3. **Animer en changeant des propriétés de contrôles (U3)** : à signaler comme « moteur d'animation UI » ; l'équivalent le plus proche de « moteur d'animation » des deux autres piles est l'**animation de composition** (`CompositionAnimation`, serveur). Mesurer **les deux** et les distinguer dans `NOTES`, sinon comparaison inéquitable avec QML/Slint (animations évaluées hors code applicatif).
4. **`ReflectionBinding`/`new Binding("Path")` en AOT** : `RequiresUnreferencedCode` (`ReflectionBinding.cs:19-20`) ; utiliser `CompiledBinding.Create`/observables ; le journal d'optimisation doit citer `improving-performance` (« Use CompiledBindings »).
5. **`INotifyPropertyChanged` levé depuis un fil de fond** : chaque événement est re-posté (`WeakEvents.cs:27-48`) ; c'est un piège de perf **et** de famine d'entrées ; coalescer côté appli, lever sur l'UI une fois par frame (`Dispatcher.UIThread.Post` unique).
6. **Poster à priorité ≥ `Default` sans borne** : affame X11 (`Dispatcher.Queue.cs:173`) ; pour des tâches de fond non critiques utiliser `DispatcherPriority.Background`/`Input` (qui cèdent devant l'entrée, `:176-185`) — mais attention à l'équité de F2/L3 (compter ce qui est appliqué).
7. **Matérialiser 10 M d'items** : préférer une `IList` + `INotifyCollectionChanged` virtuelle (O(1) setup) ; si ce n'est pas fait, la mémoire/GC du setup domine L1 et L4 ; tout `IEnumerable` non-`IList` est **copié** (`ItemsSourceView.cs:280-282`).
8. **`ObservableCollection` modifiée hors UI** ou événements structurels un par un : coût de remesure à chaque opération ; grouper (une `NotifyCollectionChangedAction.Reset` par lot si la spec le permet, à documenter).
9. **`CacheLength`** : défaut 0 (`VirtualizingStackPanel.cs:58-60`) ; l'augmenter est une optimisation documentée par l'API (propriété publique) et réduit les remesures, mais change le nombre d'éléments réalisés ⇒ à justifier et à égalité avec le `cacheBuffer` de QML.
10. **`UseRetainedFramebuffer`** et **`CompositionOptions.UseRegionDirtyRectClipping`** : options **publiques** documentées, très favorables au chemin logiciel ; à activer (et journaliser) dans les trois bancs Avalonia comme optimisations v1 avec preuve (`X11Platform.cs:500-507`, `CompositionOptions.cs:11`). `RenderingMode` doit être fixé à `Software` pour éviter un repli GLX/EGL incertain sous Xvfb.
11. **`BENCH_PACING=uncapped`** : non réalisable sans API privée (`IRenderTimer`, `IRenderLoop` en `[PrivateApi]`) ⇒ le déclarer `unsupported` plutôt que de bricoler la réflexion.
12. **Texte : un `TextBlock` géant pour T1/T3** teste le pire cas (formatage total, pas de cull) ; une liste virtualisée de paragraphes contourne la limite mais change l'API de sélection (« tout sélectionner ») ; décider avec les autres piles (Qt/Slint) et le noter explicitement.
13. **Images** : `Bitmap` décodé à chaque frame au lieu d'une fois ; `BitmapInterpolationMode.HighQuality` par défaut = Mitchell en agrandissement ; `LowQuality` est l'équivalent « bilinéaire » des autres piles, à aligner et à noter.
14. **Overlays de diagnostic** (`DebugOverlays`) à ne jamais activer pendant les mesures (dessinées dans le tampon).
15. **Mesure du thread UI (`ui_stall_ms_max`)** : un `DispatcherTimer` sans argument tourne à priorité `Background` (`AB/Threading/DispatcherTimer.cs:18-19`), qui cède devant l'entrée et sera retardé par la file ; choisir explicitement une priorité (`Render`+) pour qu'il ne soit pas lui-même retardé par la file ; le GC arrête ce minuteur comme le reste.
16. **G3 chart** : construire le chemin de 1 M points chaque frame (conversion `Point`→`SKPoint`) ajoute 3–8 ms managés ; stocker les points déjà au format Skia (`SKPoint[]`) dans une `ICustomDrawOperation` fait partie de l'optimisation légitime mais utilise `ISkiaSharpApiLeaseFeature` (`[Unstable]`) : le consigner en `NOTES`.
17. **Journal d'optimisation** : prévoir les sources citables pour Avalonia — `improving-performance` (docs), `X11PlatformOptions.UseRetainedFramebuffer` (XML doc, `X11Platform.cs:500-507`), `CompositionOptions` (`:11-33`), `VirtualizingStackPanel.CacheLength`, `RenderOptions.*`, `Bitmap.DecodeToWidth`.
