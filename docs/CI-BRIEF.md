## Contraintes de l'environnement (vérifiées)
- **Tu ne peux ni déclencher, ni lister, ni lire les exécutions GitHub Actions par l'API** (le proxy bloque `gh api …/actions`). Le seul déclencheur est un `git push` sur `ci/<stack>` (workflow `on: push: branches: ['ci/<stack>']`) ; les résultats reviennent par `git` : l'action `publish-results` les commit dans la branche `ci-results` sous `<stack>/<sha>/<artefact>/`. Attends-les avec `ci/wait_results.sh <stack> <sha>` (sonde `git fetch` toutes les 30 s, délai 40 min par défaut). **N'utilise jamais `workflow_dispatch`.** Le workflow doit toujours publier même en cas d'échec (`if: always()`), avec les journaux complets : c'est ton seul moyen de voir les erreurs.
- Chaque aller-retour coûte de 5 à 40 minutes : regroupe tes corrections, ne pousse pas toutes les minutes, teste localement tout ce qui est testable (le conteneur est un Linux x64 de 4 vCPU, sans GPU ni appareil mobile ; Xvfb, Rust 1.99.1, .NET SDK 10.0.403 dans `/opt/dotnet10`, JDK 25, Qt 6.12 dans `/opt/Qt`, Android SDK absent — il est sur le runner).
- Runners (libellés exacts) : `ubuntu-24.04` (x64, 4 vCPU, 16 Go, **KVM**, Android SDK/NDK 27.3 · 29 · 30, Chrome 155 + chromedriver, .NET 10.0.401, Rust 1.99.0, cmake 3.31, JDK 17), `ubuntu-24.04-arm`, `windows-2025` (4 vCPU, .NET 10.0.402, Rust 1.99.1, Visual Studio), `macos-26` (arm64, 3 vCPU, 7 Go, Xcode 26.6 et 26.x, simulateurs iOS 26.2/26.4/26.5, Rust 1.99.1, .NET 10.0.402), `macos-15` (arm64). N'utilise **aucun autre libellé** (un libellé inexistant laisse le job en file sans qu'on puisse l'annuler). Dépôt public : minutes gratuites, mais limite de concurrence (≈ 20 jobs Linux/Windows, 5 macOS) : n'abuse pas, `timeout-minutes` sur chaque job (≤ 60), `fail-fast: false`.
- Actions : épingle les **dernières versions majeures** (vérifiées le 2026-10-26 : `actions/checkout@v7`, `actions/upload-artifact@v7`, `actions/download-artifact@v8`, `actions/setup-dotnet@v6`, `actions/setup-java@v6`, `actions/cache@v6`, `dtolnay/rust-toolchain@v1`, `android-actions/setup-android@v4`, `Swatinem/rust-cache@v2`, `jurplel/install-qt-action@v4`). Vérifie toute autre action avec `git ls-remote --tags`. Épingle les versions des outils (Rust 1.99.1, .NET 10.0.403 via `global.json` ou setup-dotnet, Qt 6.12.0, etc.) et note les versions réelles dans les résultats. Pas de secrets, pas de signature, pas de publication : `permissions: contents: read` partout, sauf le job de publication (`contents: write`).
- Ne désactive jamais la vérification TLS ; n'utilise que des sources officielles.

## Ce que tu dois livrer, par plateforme (6 : linux, windows, macos, ios-sim, android, web)
**Étape 1 (priorité) : le build** — une app identique à `docs/SPIKE-SPEC.md` (code UI partagé ; seules les têtes de plateforme diffèrent), en **release**, dans `spikes/<stack>/`, avec le cœur vérifié de ta stack. Pour chaque plateforme : statut, artefact, tailles (brute, gzip, brotli — `ci/record.py`), durée, avertissements, erreurs **exactes** si échec, et **ce qu'il a fallu écrire à la main** (fichiers de projet Xcode/Gradle/HTML, scripts, contournements) avec le nombre de lignes. Un échec est un résultat : ne simule rien ; si une plateforme ne peut pas être construite avec le langage de la stack, dis précisément pourquoi, ce qu'il faudrait (par ex. une tête en autre langage) et si ça casse la contrainte « un seul langage ».
**Étape 2 : l'exécution** — Android : émulateur sur `ubuntu-24.04` avec KVM (`reactivecircus/android-emulator-runner` : vérifie sa dernière version) ; iOS : `xcrun simctl` sur `macos-26` ; web : Chrome headless ; bureau : Xvfb (Linux), session interactive (Windows, macOS). Récupère les marqueurs `SPIKE:*`, une capture d'écran par plateforme (PNG dans l'artefact), le démarrage à froid (`am start -W`, `simctl launch`, temps jusqu'à `SPIKE:ready`), la RAM (`dumpsys meminfo`, `ps`/`footprint`, JS heap) et le FPS du canvas. **Ce sont des chiffres d'émulateur, de simulateur et de rendu logiciel : ne les présente jamais comme des chiffres d'appareil.**
Tu dois lire toi-même au moins une capture par plateforme (outil Read sur le PNG) pour confirmer que l'UI est correcte avant de déclarer un succès.
