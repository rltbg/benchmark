# Brief commun aux agents d'implémentation (lis BENCH-SPEC.md en entier d'abord)

Contexte : comparaison de stacks UI natives multiplateformes, priorité performance. Tu implémentes l'app de référence de BENCH-SPEC.md dans UNE stack, en release, rendu LOGICIEL, sous Xvfb.
Le conteneur : 4 vCPU, 16 Go, Linux x86_64, pas de GPU, pas d'appareil mobile. D'autres agents compilent en parallèle : utilise au plus 2 jobs de build (CARGO_BUILD_JOBS=2, `-j2`, `--max-workers=2`...).

Règles dures :
- Travaille UNIQUEMENT dans ton dossier /home/user/eval/stacks/<stack>/. Ne modifie pas BENCH-SPEC.md, core/, harness/, assets/ (lecture seule).
- N'utilise PAS apt/dpkg (déjà préinstallé : Xvfb, xdotool, Mesa llvmpipe, GTK3/4, Qt6 6.4 + QML, SDL2, clang, cmake, ninja, polices Noto/DejaVu, Zig via `python3 -m ziglang`). Si un paquet système manque, note-le dans ton rapport comme bloquant au lieu de l'installer.
- Réseau : sortie HTTPS via proxy ; hôtes autorisés connus : index.crates.io, static.crates.io, static.rust-lang.org, pypi.org, registry.npmjs.org, repo.maven.apache.org, maven.google.com, plugins.gradle.org, services.gradle.org, api.nuget.org, archive.ubuntu.com, storage.googleapis.com (artefacts Flutter), pub.dev, raw.githubusercontent.com, et `git clone` anonyme de dépôts GitHub publics. BLOQUÉS : github.com (pages/releases/archives codeload), docs.rs, slint.dev, avaloniaui.net, nsh.dev, flutter.dev, ziglang.org, download.qt.io, download.swift.org, dl.google.com, opam.ocaml.org. Ne contourne JAMAIS un blocage et ne désactive jamais la vérification TLS ; si un hôte est bloqué, note lequel et cherche une source autorisée (crates, Maven Central, git clone) ou documente l'échec.
- Ne lance PAS de mesures officielles : seulement des tests de fumée courts (≤ 15 s par scénario). Je (le coordinateur) lance les mesures de façon séquentielle pour qu'elles ne se perturbent pas. Teste ton binaire avec : `Xvfb :NN -screen 0 1280x720x24 &` puis `DISPLAY=:NN LIBGL_ALWAYS_SOFTWARE=1 ./app --scenario list --duration 8 --out /tmp/x.json --assets /home/user/eval/assets`, et valide le JSON (frame_ms non vide, ops.sum_heights == 8799584 pour list/stream/stress). Le harnais `python3 /home/user/eval/harness/run_bench.py --stack X --cmd "<binaire>" --scenario list --duration 8 --runs 1` peut servir pour un essai.
- Fidélité : même contenu, mêmes tailles, mêmes scripts que la spec. Utilise l'idiomatique performante de la stack (pas de code lent exprès, pas de triche). Si un scénario est impossible ou injouable dans la stack, NE le simule pas : écris-le dans le JSON (`"unsupported": "raison"`) et dans ton rapport — c'est un résultat.
- Priorité des scénarios : idle, list, stream, canvas, core, stress d'abord ; puis text, images, nav.
- Garde les erreurs exactes (compilation, exécution) dans /home/user/eval/stacks/<stack>/logs/ (copie les logs bruts de build).
- Écris /home/user/eval/stacks/<stack>/STACK-NOTES.md : versions exactes (outils, crates/paquets avec versions), commande de build, commande de lancement du binaire pour le harnais, ce qui est implémenté / partiel / non supporté et pourquoi, contournements, écarts à la spec, taille du binaire et des bibliothèques/runtimes nécessaires à l'exécution (liste `ldd` + tailles, taille du dossier de déploiement), nombre de lignes de ton code applicatif, bugs rencontrés avec messages exacts, temps de compilation.
- Rapport final (court, ≤ 40 lignes) : chemin du binaire/commande, scénarios OK/partiels/KO, résultats de fumée bruts (FPS approximatifs), problèmes bloquants. Ne prétends rien que tu n'as pas exécuté.

## Ajouts (incidents constatés)
- NE LANCE JAMAIS `pkill Xvfb`/`killall Xvfb` : d'autres agents et le harnais (displays :90–:98) utilisent leurs propres Xvfb. Démarre le tien sur un numéro aléatoire entre :200 et :699 et ne tue que ton PID.
- Dans `notes` du JSON, dis précisément quel événement marque la « fin de frame » (présentation réelle vs début de callback vs signal « rendu » du toolkit) et signale si le toolkit émet des signaux de frame sans changement à l'écran. Ne gonfle jamais les FPS : compte uniquement des frames réellement redessinées avec un contenu qui a changé.
- Si une dépendance est bloquée par le réseau, ne cherche pas de miroir tiers non listé : documente l'erreur exacte et la conséquence (version rétrogradée, fonction manquante).
